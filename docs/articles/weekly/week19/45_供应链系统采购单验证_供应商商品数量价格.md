## 引言

在 ERP / SCM / 采购管理系统里，**采购单**是最核心、也最容易出问题的业务单据之一。它看起来也不复杂——选个供应商、填几行商品、写个数量和单价，好像就是几张表格的事。

恰恰相反。采购单是**中国企业信息化里规则最琐碎、数据关系最复杂、又最容易因为一个数字出错就造成重大损失**的一类业务数据：

- **供应商信息多**：统一社会信用代码、联系人、手机号、银行账号……每种都有严格的格式要求，错一位就可能付款到错误的账户；
- **商品信息杂**：SKU 编码、商品条码（EAN/ISBN）、品名、规格、计量单位……不同品类的规则完全不同；
- **金额勾稽严**：数量 × 单价 = 金额，金额 × 税率 = 税额，价税合计 = 金额 + 税额……一环错，环环错；
- **合规要求高**：涉及合同法、税法、发票管理办法，错误数据可能导致税务风险或合同纠纷。

本文把采购单的数据验证拆成四块讲透——**供应商信息（信用代码 + 联系方式 + 银行账户）、商品信息（SKU + 条码 + 品名 + 规格）、数量与价格（采购量 + 单价 + 金额勾稽 + 税率）、交货与物流（日期 + 地址 + 快递单号）**，并给出可以直接落地的 ValidX 实现。文章最后会重点澄清几个常见误区：**统一社会信用代码有校验位**、**金额计算必须用 BigDecimal 而不是 double**、**采购单价允许 0 元（赠品场景）但需要特殊标记**。

## 一、采购单数据验证的全景

### 1.1 一张采购单的数据生命周期

先建立全局观。一张采购单从创建到完成，可以分为三个阶段——每个阶段需要校验的字段和规则各不相同：

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   创建阶段    │ ──► │   审批阶段    │ ──► │   执行阶段    │
│              │     │              │     │              │
│ · 供应商信息  │     │ · 预算校验    │     │ · 交货日期    │
│ · 商品明细    │     │ · 金额审批    │     │ · 收货地址    │
│ · 数量与单价  │     │ · 合规审查    │     │ · 物流单号    │
│ · 交货要求    │     │ · 合同关联    │     │ · 签收确认    │
└──────────────┘     └──────────────┘     └──────────────┘
   格式 + 规则为主       业务合规为主         时间线 + 完整性
```

| 阶段 | 核心校验对象 | 校验本质 |
|------|------------|---------|
| **创建** | 供应商信用代码、商品 SKU、数量、单价、金额 | 格式合法性 + 数学正确性 |
| **审批** | 采购总额、预算余额、合同关联、审批权限 | 业务合规 + 权限控制 |
| **执行** | 交货日期、收货地址、物流单号、签收状态 | 时间线约束 + 完整性 |

### 1.2 采购数据验证的 4 个层次

| 层次 | 做什么 | 能挡住什么 | 需要什么 |
|------|--------|-----------|---------|
| **L1 格式校验** | 长度、字符集、正则 | 手输错位、粘贴乱码 | 正则 / ValidX 注解 |
| **L2 算法校验** | 信用代码校验位、银行卡 Luhn、EAN 校验位 | 伪造编码、输错一位的卡号 | mod 校验算法 |
| **L3 关系校验** | 金额勾稽、日期先后、数量与单位一致性 | 金额不平、日期倒挂 | 跨字段校验 |
| **L4 业务合规** | 预算上限、审批权限、供应商准入状态 | 超预算采购、向不合格供应商下单 | 业务规则引擎 |

**关键认知**：前 3 层是**本地可做的**（本文的重点），第 4 层**需要结合企业政策和外部系统**——本文会涉及，但会标注"这是业务规则，不是格式规则"。

### 1.3 为什么采购数据最容易"出事"

在企业数据治理领域有一个共识：**采购数据是最容易引发经济损失的**。原因不是技术复杂，而是：

- **录入来源杂**：采购员手工录入、供应商自助提交、Excel 批量导入、EDI 电子数据交换……每个入口都可能引入脏数据；
- **数据关系密**：数量、单价、金额、税率、税额之间存在**数学勾稽关系**——一个数字错了，后续所有计算都错；
- **金额敏感**：一个小数点错位，就可能从"采购 1000 元"变成"采购 10000 元"；
- **外部依赖多**：供应商信息、商品信息、汇率、税率……都依赖外部数据源，任何一方的变更都可能引发数据不一致。

```java
// 反例：用 double 计算金额
double total = 100.0 * 0.35;  // 35.0
double total2 = 100.0 * 0.35; // 35.00000000000001？不，这里恰好是 35.0
// 但换成：
double total3 = 0.1 + 0.2;    // 0.30000000000000004！
```

| 输入场景 | 上面的代码能正确处理吗 | 应该怎么做 |
|---------|---------------------|-----------|
| `1000 × 0.15` | ❌ 结果可能是 `150.00000000000002` | 用 `BigDecimal` |
| `单价 0.001 元`（大宗原料）| ❌ `double` 精度不够 | 用 `BigDecimal` + 足够的小数位 |
| `金额 99999999.99` | ❌ 超出 `double` 精确表示范围 | 用 `BigDecimal` |

**真正的对策**：所有金额计算一律使用 `BigDecimal`——这不是最佳实践，而是**强制要求**。

## 二、供应商信息验证：信用代码、联系方式、银行账户

### 2.1 统一社会信用代码：供应商的"身份证"

每个合法的中国企业都有一个**统一社会信用代码**（18 位），它是供应商身份的基石。ValidX 的 `@UnifiedSocialCreditCode` 内置了完整的校验逻辑：

```
┌────┬────────┬──────────┬──────────┬───────┐
│ 1位 │  1位   │   6位    │   9位    │  1位  │
│登记│  机构  │  登记管理 │  主体标识│ 校验位│
│管理部门│ 类别  │  行政区划│  (组织机构代码)│       │
└────┴────────┴──────────┴──────────┴───────┘
```

- **第 1 位**：登记管理部门代码（1-9, A, N）；
- **第 2 位**：机构类别代码；
- **第 3-8 位**：登记管理机关行政区划代码；
- **第 9-17 位**：主体标识码（组织机构代码）；
- **第 18 位**：校验码（mod 31 算法）。

```java
// ValidX 一行搞定
@UnifiedSocialCreditCode(message = "统一社会信用代码格式不正确")
private String supplierCreditCode;
```

**链式 API 版本**（适合从 Map/JSON 动态校验）：

```java
ValidX v = ValidX.init().withLocale(Locale.SIMPLIFIED_CHINESE);
v.field("统一社会信用代码").isUnifiedSocialCreditCode(supplierData.get("creditCode"));
```

#### 2.1.1 供应商名称

供应商名称应与营业执照一致，通常是**中文公司名称**，包含"公司""集团""厂""店"等后缀：

```java
@NotBlank(message = "供应商名称不能为空")
@Size(min = 2, max = 100, message = "供应商名称长度需在 2-100 字之间")
private String supplierName;
```

> **实战建议**：如果系统需要严格校验"名称是否包含公司类型后缀"（如"有限公司""有限责任公司""股份有限公司"等），这属于**业务规则**——在 Service 层做正则匹配或白名单校验，而不是在格式注解中硬编码。

#### 2.1.2 供应商编码

供应商编码是企业内部对供应商的唯一标识，常见规则：

| 规则 | 示例 | 校验方式 |
|------|------|---------|
| 纯数字定长 | `100234` | `@FixedLength(length = 6)` |
| 前缀 + 序号 | `SUP00001` | `@Pattern(regexp = "^SUP\\d{5}$")` |
| 字母数字组合 | `S10234A` | `@AlphaNumber` |

```java
@NotBlank(message = "供应商编码不能为空")
@Pattern(regexp = "^SUP\\d{5}$", message = "供应商编码格式不正确（SUP+5位数字）")
private String supplierCode;
```

### 2.2 供应商联系方式

| 字段 | 校验要点 | ValidX 注解 |
|------|---------|------------|
| 联系人姓名 | 中文字符、2-20 字 | `@ChineseName` |
| 手机号 | 11 位、号段合法 | `@ChinesePhone` |
| 座机号 | 区号 + 号码 + 分机号 | `@ChineseLandline` |
| 手机或座机 | 两者满足其一即可 | `@ChinesePhoneOrLandline` |
| 邮箱 | RFC 5322 格式 | `@Email` |
| 供应商地址 | 中文地址 | `@ChineseAlphaDash` |
| 邮政编码 | 6 位数字 | `@ChineseZipCode` |

```java
@Data
public class SupplierContactDTO {

    /** 联系人姓名 */
    @NotBlank(message = "联系人姓名不能为空")
    @ChineseName(message = "联系人姓名格式不正确")
    private String contactName;

    /** 手机号 */
    @NotBlank(message = "手机号不能为空")
    @ChinesePhone(message = "手机号格式不正确")
    private String phone;

    /** 座机号（可选） */
    @ChineseLandline(message = "座机号格式不正确")
    private String landline;

    /** 邮箱 */
    @Email(message = "邮箱格式不正确")
    private String email;

    /** 供应商地址 */
    @Size(max = 200, message = "供应商地址不能超过 200 字")
    private String address;

    /** 邮政编码 */
    @ChineseZipCode(message = "邮政编码格式不正确")
    private String zipCode;
}
```

### 2.3 供应商银行账户

采购单最终要付款，供应商银行账户信息的校验至关重要：

```java
@Data
public class SupplierBankDTO {

    /** 开户名称（应与供应商名称一致——跨字段校验） */
    @NotBlank(message = "开户名称不能为空")
    @Size(min = 2, max = 100, message = "开户名称长度需在 2-100 字之间")
    private String bankAccountName;

    /** 银行账号 */
    @NotBlank(message = "银行账号不能为空")
    @BankCard(message = "银行账号格式不正确")
    private String bankAccountNo;

    /** 开户行名称 */
    @NotBlank(message = "开户行不能为空")
    @Size(min = 2, max = 50, message = "开户行长度需在 2-50 字之间")
    private String bankName;

    /** SWIFT Code（跨境付款时需要） */
    @SWIFT(message = "SWIFT Code 格式不正确")
    private String swiftCode;

    /** IBAN（欧洲跨境付款时需要） */
    @IBAN(message = "IBAN 格式不正确")
    private String iban;
}
```

> **关于 `@BankCard`**：ValidX 的 `@BankCard` 内置了 **Luhn 算法**（mod 10）校验，可以检测出大多数因手输错误导致的无效银行卡号。但请注意：Luhn 校验通过 ≠ 银行卡一定存在，只是说明格式上合法。

### 2.4 ValidX 实现

把上面的供应商 DTO 组合起来：

```java
@Data
public class SupplierDTO {

    // ==================== 基础信息 ====================

    @NotBlank(message = "供应商编码不能为空")
    @Pattern(regexp = "^SUP\\d{5}$", message = "供应商编码格式不正确")
    private String supplierCode;

    @NotBlank(message = "供应商名称不能为空")
    @Size(min = 2, max = 100, message = "供应商名称长度需在 2-100 字之间")
    private String supplierName;

    @NotBlank(message = "统一社会信用代码不能为空")
    @UnifiedSocialCreditCode(message = "统一社会信用代码格式不正确")
    private String creditCode;

    // ==================== 联系信息 ====================

    @NotBlank(message = "联系人姓名不能为空")
    @ChineseName(message = "联系人姓名格式不正确")
    private String contactName;

    @NotBlank(message = "手机号不能为空")
    @ChinesePhone(message = "手机号格式不正确")
    private String contactPhone;

    @Email(message = "邮箱格式不正确")
    private String contactEmail;

    @ChineseZipCode(message = "邮政编码格式不正确")
    private String zipCode;

    // ==================== 银行信息 ====================

    @NotBlank(message = "开户名称不能为空")
    private String bankAccountName;

    @NotBlank(message = "银行账号不能为空")
    @BankCard(message = "银行账号格式不正确")
    private String bankAccountNo;

    @NotBlank(message = "开户行不能为空")
    @Size(min = 2, max = 50, message = "开户行长度需在 2-50 字之间")
    private String bankName;

    // ==================== 供应商状态 ====================

    @NotBlank(message = "供应商状态不能为空")
    @In({"PENDING", "APPROVED", "SUSPENDED", "BLACKLISTED"},
        message = "供应商状态不在合法范围内")
    private String status;

    @NotBlank(message = "供应商类型不能为空")
    @In({"MATERIAL", "SERVICE", "EQUIPMENT", "LOGISTICS", "OTHER"},
        message = "供应商类型不在合法范围内")
    private String supplierType;
}
```

**跨字段校验**（开户名 = 供应商名称）：

```java
@Service
public class SupplierBankValidator {

    public void validateBankAccount(SupplierDTO supplier) {
        ValidX v = ValidX.init().withLocale(Locale.SIMPLIFIED_CHINESE);

        // 开户名应与供应商名称一致
        if (supplier.getBankAccountName() != null
                && supplier.getSupplierName() != null
                && !supplier.getBankAccountName().contains(supplier.getSupplierName())
                && !supplier.getSupplierName().contains(supplier.getBankAccountName())) {
            v.field("开户名称").getErrors()
             .add("开户名称（" + supplier.getBankAccountName()
                + "）与供应商名称（" + supplier.getSupplierName() + "）不一致");
        }

        if (!v.passed()) {
            throw new PurchaseValidationException(v.getErrors());
        }
    }
}
```

> **注意**：开户名称和供应商名称不一定完全相同（如"北京XX科技有限公司" vs "XX科技"），所以这里用的是**包含关系**判断，而不是严格相等。具体策略取决于业务要求。

## 三、商品信息验证：SKU、品名、规格、分类

### 3.1 SKU 编码规则

SKU（Stock Keeping Unit，库存量单位）是商品的内部标识编码，不同企业的 SKU 规则差异很大：

| 规则 | 示例 | 校验方式 |
|------|------|---------|
| 纯数字定长 | `1002345678` | `@FixedLength(length = 10)` |
| 分类码 + 序号 | `EL-2026-00001` | `@Pattern(regexp = "^[A-Z]{2}-\\d{4}-\\d{5}$")` |
| 字母数字组合 | `SKU10234A` | `@AlphaNumber` |

```java
@NotBlank(message = "SKU 编码不能为空")
@Pattern(regexp = "^[A-Z]{2,4}-\\d{4,8}(-[A-Z0-9]{1,4})?$",
         message = "SKU 编码格式不正确")
private String skuCode;
```

> **关于 SKU 的设计**：SKU 编码规则是企业内部的编码规范，ValidX 负责**格式校验**（是否符合编码规则），但"SKU 是否在商品主数据中存在"属于**业务校验**——需要查数据库。

### 3.2 商品条码：EAN / ISBN

如果采购的商品有标准条码（如零售商品、图书），ValidX 提供了专门的注解：

| 条码类型 | 说明 | ValidX 注解 |
|---------|------|------------|
| EAN-13 / EAN-8 | 国际商品条码（零售商品最常见） | `@Pattern` + 校验位算法 |
| ISBN-10 / ISBN-13 | 图书编号 | `@ISBN` |

```java
/** 商品条码（EAN-13） */
@Pattern(regexp = "^\\d{13}$", message = "EAN 条码必须为 13 位数字")
private String eanCode;

/** 图书 ISBN（如果是图书类商品） */
@ISBN(message = "ISBN 格式不正确")
private String isbnCode;
```

### 3.3 品名与规格

| 字段 | 校验要点 | ValidX 注解 |
|------|---------|------------|
| 商品名称 | 非空、长度限制、不含特殊字符 | `@NotBlank` + `@Size` |
| 规格型号 | 字母数字组合、允许中文 | `@ChineseAlphaDash` |
| 计量单位 | 枚举值（个/箱/吨/米/升等） | `@In` |
| 品牌 | 中文字符 | `@Chinese` |
| 产地 | 中文地址 | `@ChineseAlphaDash` |

```java
@Data
public class ProductItemDTO {

    /** SKU 编码 */
    @NotBlank(message = "SKU 编码不能为空")
    @Pattern(regexp = "^[A-Z]{2,4}-\\d{4,8}(-[A-Z0-9]{1,4})?$",
             message = "SKU 编码格式不正确")
    private String skuCode;

    /** 商品名称 */
    @NotBlank(message = "商品名称不能为空")
    @Size(min = 1, max = 200, message = "商品名称长度需在 1-200 字之间")
    private String productName;

    /** 规格型号 */
    @Size(max = 100, message = "规格型号不能超过 100 字")
    private String specification;

    /** 计量单位 */
```

## 四、数量与价格验证：采购量、单价、金额勾稽

### 4.1 采购数量：不只是"大于 0"

采购数量的校验远比想象中复杂：

```
┌─────────────────────────────────────────────────────────┐
│  采购数量的校验规则                                       │
│                                                         │
│  ① 数量 > 0（赠品场景允许 0，但需特殊标记）               │
│  ② 数量精度 ≤ 计量单位允许的小数位                       │
│     · 个/箱/套 → 整数                                    │
│     · 千克/米/升 → 最多 2-6 位小数                       │
│  ③ 数量不能超过采购上限（业务规则）                       │
│  ④ 数量与计量单位的合理性                                │
│     · 采购 0.001 吨钢材 → 合理                           │
│     · 采购 0.001 台电脑 → 不合理                         │
└─────────────────────────────────────────────────────────┘
```

**计量单位与数量精度的关系**：

```java
@Service
public class QuantityPrecisionValidator {

    /** 整数计量单位 */
    private static final Set<String> INTEGER_UNITS = Set.of(
            "PIECE", "BOX", "CARTON", "SET", "PALLET");

    /** 最多 2 位小数的计量单位 */
    private static final Set<String> TWO_DECIMAL_UNITS = Set.of(
            "KILOGRAM", "METER", "LITER");

    /**
     * 校验数量精度与计量单位的一致性
     */
    public void validateQuantityPrecision(BigDecimal quantity, String unit) {
        ValidX v = ValidX.init().withLocale(Locale.SIMPLIFIED_CHINESE);

        if (INTEGER_UNITS.contains(unit)) {
            // 整数单位：数量必须是整数
            if (quantity.scale() > 0 &&
                    quantity.stripTrailingZeros().scale() > 0) {
                v.field("采购数量").getErrors()
                 .add("计量单位为「" + unit + "」时，采购数量必须为整数");
            }
        } else if (TWO_DECIMAL_UNITS.contains(unit)) {
            // 2 位小数单位
            if (quantity.scale() > 2) {
                v.field("采购数量").getErrors()
                 .add("计量单位为「" + unit + "」时，采购数量最多 2 位小数");
            }
        }
        // 其他单位（吨等）允许更多小数位

        if (!v.passed()) {
            throw new PurchaseValidationException(v.getErrors());
        }
    }
}
```

### 4.2 单价：精度与合理区间

单价的校验有两个关键点：

1. **精度**：不同行业的单价精度不同——零售商品通常 2 位小数，大宗原料可能需要 4-6 位小数；
2. **合理区间**：单价偏离历史均价太多（如 10 倍以上），可能是录入错误。

```java
/** 单价精度校验 */
@NotNull(message = "单价不能为空")
@DecimalMin(value = "0.00", message = "单价不能为负数")
@Digits(integer = 12, fraction = 4, message = "单价最多 4 位小数")
private BigDecimal unitPrice;
```

> **关于"单价为 0"**：赠品、样品、调拨等场景下，单价可以为 0。但系统应该要求标记**价格类型**（正常/赠品/样品），以便后续审计区分。

### 4.3 金额的数学勾稽关系

这是采购单校验中**最有价值的部分**——和财务系统一样，采购单也有严格的数学关系：

```
① 金额 = 数量 × 单价
② 税额 = 金额 × 税率
③ 价税合计 = 金额 + 税额
④ 采购总额 = Σ 各行价税合计
```

**校验实现**：

```java
public final class PurchaseReconciliation {

    /** 金额容差（分位四舍五入） */
    private static final BigDecimal TOLERANCE = new BigDecimal("0.01");

    /**
     * 校验：金额 = 数量 × 单价
     */
    public static boolean checkAmount(BigDecimal quantity,
                                      BigDecimal unitPrice,
                                      BigDecimal amount) {
        if (quantity == null || unitPrice == null || amount == null) {
            return false;
        }
        BigDecimal expected = quantity.multiply(unitPrice)
                .setScale(2, RoundingMode.HALF_UP);
        return amount.subtract(expected).abs()
                .compareTo(TOLERANCE) <= 0;
    }

    /**
     * 校验：税额 = 金额 × 税率
     */
    public static boolean checkTaxAmount(BigDecimal amount,
                                         BigDecimal taxRate,
                                         BigDecimal taxAmount) {
        if (amount == null || taxRate == null || taxAmount == null) {
            return false;
        }
        BigDecimal expected = amount.multiply(taxRate)
                .setScale(2, RoundingMode.HALF_UP);
        return taxAmount.subtract(expected).abs()
                .compareTo(TOLERANCE) <= 0;
    }

    /**
     * 校验：价税合计 = 金额 + 税额
     */
    public static boolean checkTotalAmount(BigDecimal amount,
                                           BigDecimal taxAmount,
                                           BigDecimal totalAmount) {
        if (amount == null || taxAmount == null || totalAmount == null) {
            return false;
        }
        BigDecimal expected = amount.add(taxAmount)
                .setScale(2, RoundingMode.HALF_UP);
        return totalAmount.subtract(expected).abs()
                .compareTo(TOLERANCE) <= 0;
    }

    /**
     * 校验：采购总额 = 各行价税合计之和
     */
    public static boolean checkGrandTotal(List<PurchaseItemDTO> items,
                                          BigDecimal grandTotal) {
        if (items == null || items.isEmpty() || grandTotal == null) {
            return false;
        }
        BigDecimal sum = items.stream()
                .map(PurchaseItemDTO::getTotalAmount)
                .filter(Objects::nonNull)
                .reduce(BigDecimal.ZERO, BigDecimal::add);
        return grandTotal.subtract(sum).abs()
                .compareTo(TOLERANCE) <= 0;
    }
}
```

> **`compareTo` 而不是 `equals`**：这是采购单校验中最容易犯的错误——`BigDecimal` 的 `equals` 会比较精度，`new BigDecimal("100.0").equals(new BigDecimal("100.00"))` 返回 `false`。金额比较**必须用 `compareTo`**。

### 4.4 税率与税额

中国常见的增值税税率：

| 税率 | 适用范围 |
|------|---------|
| 13% | 销售货物、加工修理修配劳务、有形动产租赁 |
| 9% | 交通运输、邮政、基础电信、建筑、不动产租赁、农产品 |
| 6% | 现代服务、生活服务、增值电信、金融、销售无形资产 |
| 5% | 简易计税方法的不动产销售 |
| 3% | 小规模纳税人征收率 |
| 1% | 小规模纳税人优惠征收率（阶段性政策） |
| 0% | 出口货物、跨境服务 |

```java
@NotNull(message = "税率不能为空")
@DecimalMin(value = "0", message = "税率不能为负数")
@DecimalMax(value = "1", message = "税率不能大于 1")
@Digits(integer = 1, fraction = 4, message = "税率格式不正确")
private BigDecimal taxRate;
```

> **注意**：税率用**小数**（0.13）而不是**百分比**（13）存储，这是财务系统的通用做法。如果用百分比存储，`@DecimalMax` 的值需要改为 `"100"`。

### 4.5 ValidX 实现

采购明细行的完整校验在 Service 层完成：

```java
@Service
public class PurchaseItemValidationService {

    public void validate(PurchaseItemDTO item) {
        ValidX v = ValidX.init().withLocale(Locale.SIMPLIFIED_CHINESE);

        // ============ 1. 金额 = 数量 × 单价 ============
        if (!PurchaseReconciliation.checkAmount(
                item.getQuantity(), item.getUnitPrice(), item.getAmount())) {
            v.field("金额").getErrors()
             .add("金额（" + item.getAmount() + "）≠ 数量（" + item.getQuantity()
                + "）× 单价（" + item.getUnitPrice() + "）");
        }

        // ============ 2. 税额 = 金额 × 税率 ============
        if (!PurchaseReconciliation.checkTaxAmount(
                item.getAmount(), item.getTaxRate(), item.getTaxAmount())) {
            v.field("税额").getErrors()
             .add("税额（" + item.getTaxAmount() + "）≠ 金额（" + item.getAmount()
                + "）× 税率（" + item.getTaxRate() + "）");
        }

        // ============ 3. 价税合计 = 金额 + 税额 ============
        if (!PurchaseReconciliation.checkTotalAmount(
                item.getAmount(), item.getTaxAmount(), item.getTotalAmount())) {
            v.field("价税合计").getErrors()
             .add("价税合计（" + item.getTotalAmount() + "）≠ 金额（"
                + item.getAmount() + "）+ 税额（" + item.getTaxAmount() + "）");
        }

        // ============ 4. 危险品条件校验 ============
        if (Boolean.TRUE.equals(item.getIsHazardous())
                && (item.getHazardousCode() == null
                    || item.getHazardousCode().isEmpty())) {
            v.field("危险品编号").getErrors()
             .add("危险品标识为「是」时，危险品编号不能为空");
        }

        // ============ 5. 单价为 0 时需要特殊标记 ============
        if (item.getUnitPrice() != null
                && item.getUnitPrice().compareTo(BigDecimal.ZERO) == 0
                && item.getQuantity().compareTo(BigDecimal.ZERO) > 0) {
            // 这是业务提示，不是错误——根据业务需求决定是否阻断
            v.field("单价").getErrors()
             .add("单价为 0，请确认是否为赠品/样品");
        }

        if (!v.passed()) {
            throw new PurchaseValidationException(v.getErrors());
        }
    }
}
```

```java
public void validateDeliveryTimeline(DeliveryDTO dto, String createDate) {
    ValidX v = ValidX.init().withLocale(Locale.SIMPLIFIED_CHINESE);

    LocalDate expected = LocalDate.parse(dto.getExpectedDate());
    LocalDate promised = LocalDate.parse(dto.getPromisedDate());
    LocalDate created = LocalDate.parse(createDate);

    // 期望交货日期 ≥ 采购单创建日期
    if (expected.isBefore(created)) {
        v.field("期望交货日期").getErrors()
         .add("期望交货日期不能早于采购单创建日期（" + createDate + "）");
    }

    // 承诺交货日期 ≥ 期望交货日期
    if (promised.isBefore(expected)) {
        v.field("承诺交货日期").getErrors()
         .add("承诺交货日期不能早于期望交货日期（" + dto.getExpectedDate() + "）");
    }

    // 实际交货日期（如果有）在期望和承诺之间
    if (dto.getActualDate() != null) {
        LocalDate actual = LocalDate.parse(dto.getActualDate());
        if (actual.isAfter(promised)) {
            v.field("实际交货日期").getErrors()
             .add("实际交货日期（" + dto.getActualDate()
                + "）晚于承诺交货日期（" + dto.getPromisedDate() + "），已逾期");
        }
    }

    if (!v.passed()) {
        throw new PurchaseValidationException(v.getErrors());
    }
}
```

```java
    @Size(min = 2, max = 100, message = "供应商名称长度需在 2-100 字之间")

    @UnifiedSocialCreditCode(message = "统一社会信用代码格式不正确")

    @NotBlank(message = "采购日期不能为空")
    @PastDate(includeToday = true, message = "采购日期不能晚于今天")

    @NotBlank(message = "币种不能为空")

        message = "币种不在合法范围内")
    private String currency;

    // ==================== 采购明细 ====================

    @NotEmpty(message = "采购明细不能为空")
    @Size(min = 1, max = 100, message = "采购明细行数需在 1-100 之间")
```

### 6.2 采购单校验 Service

```java
@Service
public class PurchaseOrderValidationService {

    @Autowired
    private PurchaseItemValidationService itemValidationService;

    public void validate(PurchaseOrderRequest req) {
        ValidX v = ValidX.init().withLocale(Locale.SIMPLIFIED_CHINESE);

        // ============ 1. 供应商名称与信用代码的一致性 ============
        // 信用代码对应的企业名称应与供应商名称一致
        // ← 这需要查询工商数据库，属于业务校验

        // ============ 2. 采购日期 ≤ 期望交货日期 ============
        if (req.getOrderDate() != null && req.getExpectedDate() != null) {
            LocalDate orderDate = LocalDate.parse(req.getOrderDate());
            LocalDate expectedDate = LocalDate.parse(req.getExpectedDate());
            if (expectedDate.isBefore(orderDate)) {
                v.field("期望交货日期").getErrors()
                 .add("期望交货日期不能早于采购日期（" + req.getOrderDate() + "）");
            }
        }

        // ============ 3. 期望交货日期 ≤ 承诺交货日期 ============
        if (req.getExpectedDate() != null && req.getPromisedDate() != null) {
            LocalDate expected = LocalDate.parse(req.getExpectedDate());
            LocalDate promised = LocalDate.parse(req.getPromisedDate());
            if (promised.isBefore(expected)) {
                v.field("承诺交货日期").getErrors()
                 .add("承诺交货日期不能早于期望交货日期");
            }
        }

        // ============ 4. 逐行校验采购明细 ============
        if (req.getItems() != null) {
            for (int i = 0; i < req.getItems().size(); i++) {
                PurchaseItemDTO item = req.getItems().get(i);
                try {
                    itemValidationService.validate(item);
                } catch (PurchaseValidationException e) {
                    // 将行级错误汇总到主单
                    for (String error : e.getErrors()) {
                        v.field("第 " + (i + 1) + " 行").getErrors().add(error);
                    }
                }
            }
        }

        // ============ 5. 采购总额 = 各行价税合计之和 ============
        if (req.getItems() != null && req.getGrandTotal() != null) {
            if (!PurchaseReconciliation.checkGrandTotal(
                    req.getItems(), req.getGrandTotal())) {
                v.field("采购总额").getErrors()
                 .add("采购总额与各行价税合计之和不一致");
            }
        }

        // ============ 6. 行号连续性校验 ============
        if (req.getItems() != null) {
            for (int i = 0; i < req.getItems().size(); i++) {
                String expectedLineNo = String.valueOf(i + 1);
                if (!expectedLineNo.equals(req.getItems().get(i).getLineNo())) {
                    v.field("行号").getErrors()
                     .add("第 " + (i + 1) + " 行的行号应为 " + expectedLineNo
                        + "，实际为 " + req.getItems().get(i).getLineNo());
                }
            }
        }

        if (!v.passed()) {
            throw new PurchaseValidationException(v.getErrors());
        }
    }
}
```

## 七、常见坑与规避

### 7.1 坑一：用 double 计算金额

**现象**：采购 1000 件 × 单价 0.35 元 = 350.00 元，但系统计算结果为 `350.00000000000006`，入库后金额多了 0.00000000000006 元。

**根因**：`double` 是浮点数，存在精度丢失问题。

```java
// 反例
double amount = 1000.0 * 0.35;  // 350.0（恰好正确）
double amount2 = 3.0 * 0.1;     // 0.30000000000000004（出错了！）
```

**规避**：
- DTO 中的金额字段**一律用 `BigDecimal`**；
- 金额计算**一律用 `BigDecimal.multiply()`**；
- 金额比较**一律用 `compareTo()`**，不用 `equals()`。

### 7.2 坑二：统一社会信用代码用 String 接收但没做格式校验

**现象**：供应商录入信用代码时，填了"待补充""暂无"等文字，系统照单全收。

**根因**：只做了 `@NotBlank`，没做格式校验。

**规避**：

```java
@NotBlank(message = "统一社会信用代码不能为空")
@UnifiedSocialCreditCode(message = "统一社会信用代码格式不正确")
private String creditCode;
```

### 7.3 坑三：采购数量用 Integer 接收

**现象**：采购钢材 1.5 吨，系统报错"数量格式错误"——因为 `Integer` 无法表示小数。

**根因**：不同计量单位的商品，数量精度不同。用 `Integer` 只能表示整数数量。

**规避**：
- 采购数量**一律用 `BigDecimal`**；
- 在 Service 层根据计量单位校验数量精度是否合理（见 4.1 节）。

### 7.4 坑四：税率用百分比存储

**现象**：前端传了 `taxRate = 13`（表示 13%），后端按 `amount × 13` 计算税额，结果税额是金额的 13 倍。

**根因**：前后端对税率的约定不一致——前端用百分比（13），后端用小数（0.13）。

**规避**：
- 前后端统一使用**小数**（0.13 表示 13%）；
- 在 API 文档中明确标注"税率字段为小数格式，如 0.13 表示 13%"；
- 如果必须兼容百分比格式，在 Service 层做转换：

```java
if (taxRate.compareTo(BigDecimal.ONE) > 0) {
    // 可能是百分比格式，转换为小数
    taxRate = taxRate.divide(new BigDecimal("100"), 4, RoundingMode.HALF_UP);
}
```

### 7.5 坑五：采购单行号不连续或重复

**现象**：导入 Excel 时，行号出现 `1, 2, 2, 4`（第 3 行重复，第 4 行缺失），导致后续对账时找不到对应的行。

**根因**：没有校验行号的连续性和唯一性。

**规避**：在 Service 层校验行号连续性（见 6.2 节示例）。

### 7.6 坑六：赠品/样品行单价为 0 但未标记

**现象**：审计时发现采购单中有多行单价为 0 的记录，无法判断是赠品还是录入错误。

**根因**：系统允许单价为 0，但没有要求标记原因。

**规避**：

```java
/** 价格类型 */
@NotBlank(message = "价格类型不能为空")
@In({"NORMAL", "GIFT", "SAMPLE", "ADJUSTMENT"},
    message = "价格类型不在合法范围内")
private String priceType;
```

当 `unitPrice = 0` 时，`priceType` 必须为 `GIFT` 或 `SAMPLE`——这是**条件校验**，在 Service 层处理：

```java
if (item.getUnitPrice().compareTo(BigDecimal.ZERO) == 0
        && !"GIFT".equals(item.getPriceType())
        && !"SAMPLE".equals(item.getPriceType())) {
    v.field("价格类型").getErrors()
     .add("单价为 0 时，价格类型必须为「赠品」或「样品」");
}
```

### 7.7 坑七：银行账号用 Long 接收

**现象**：银行账号 `6222021234567890123` 入库后变成了 `6222021234567890000`——末尾精度丢失。

**根因**：银行账号最长 19 位，超过了 `Long.MAX_VALUE`（约 18.4 位）。

**规避**：
- DTO 用 `String` 接收；
- 数据库用 `VARCHAR(20)`；
- **永远不要用数值类型存储标识性数字**（手机号、身份证号、银行账号同理）。

### 7.8 坑八：BigDecimal 用 equals 比较

```java
new BigDecimal("5000.0").equals(new BigDecimal("5000.00"))  // false！
new BigDecimal("5000.0").compareTo(new BigDecimal("5000.00")) // 0 → 相等
```

**规避**：金额比较**一律用 `compareTo(...) == 0`**。

## 八、总结

采购单的数据验证是"看起来简单、做对很难"的典型。本文把四块核心内容梳理如下：

### 核心知识点回顾

| 模块 | 关键结论 |
|------|---------|
| **统一社会信用代码** | 18 位 + mod 31 校验位；用 `@UnifiedSocialCreditCode` 而不是 `@Pattern` |
| **银行账号** | 有 Luhn 校验位（mod 10）；必须用 `String` 接收，不能用 `Long` |
| **SKU 编码** | 企业内部编码规则；ValidX 负责格式校验，存在性校验靠数据库 |
| **商品条码** | EAN-13 有校验位算法；图书用 `@ISBN` |
| **采购数量** | 必须用 `BigDecimal`；精度与计量单位相关（整数 vs 小数） |
| **金额勾稽** | `金额 = 数量 × 单价`、`税额 = 金额 × 税率`、`价税合计 = 金额 + 税额`；必用 `BigDecimal`，必用 `compareTo` |
| **税率** | 用小数（0.13）而不是百分比（13）；前后端必须统一约定 |
| **交货日期** | 采购日期 ≤ 期望交货日期 ≤ 承诺交货日期 |
| **物流单号** | `@ExpressNumber` 支持多种快递公司 |

### ValidX 在本场景的使用矩阵

| 需求 | 推荐用法 |
|------|---------|
| 统一社会信用代码 | `@UnifiedSocialCreditCode` |
| 供应商联系人姓名 | `@ChineseName` |
| 供应商手机号 | `@ChinesePhone` |
| 供应商座机号 | `@ChineseLandline` |
| 供应商邮箱 | `@Email` |
| 银行账号 | `@BankCard` |
| SWIFT Code | `@SWIFT` |
| IBAN | `@IBAN` |
| 图书 ISBN | `@ISBN` |
| 采购单号 | `@Pattern(regexp = "^PO\\d{4}-\\d{4,8}$")` |
| 供应商编码 | `@Pattern(regexp = "^SUP\\d{5}$")` |
| SKU 编码 | `@Pattern` |
| 商品条码 | `@Pattern(regexp = "^\\d{8,14}$")` |
| 计量单位 / 币种 / 分类 | `@In({...})` |
| 采购日期 | `@PastDate(includeToday = true)` |
| 期望/承诺交货日期 | `@FutureDate(includeToday = true)` |
| 收货人姓名 | `@ChineseName` |
| 收货人手机号 | `@ChinesePhone` |
| 收货地址 | `@ChineseAlphaDash` |
| 邮政编码 | `@ChineseZipCode` |
| 物流单号 | `@ExpressNumber` |
| 采购数量 / 单价 / 金额 | `@DecimalMin` + `@Digits` + `BigDecimal` |
| 金额勾稽 | **链式 API + BigDecimal**（跨字段） |
| 行号连续性 | **Service 层校验** |
| 供应商准入状态 | **业务规则（数据库查询）** |
| 预算校验 | **业务规则（预算系统对接）** |

**最关键的一条设计原则**（和财务系统、HR 系统完全一致）：

> **字段级校验用注解，跨字段校验用链式 API，业务合规用 Service 层规则。**

采购单的校验天然分三层——格式（注解）、关系（链式）、合规（业务规则）。把三层混在一起是万恶之源：格式规则不该出现在 Service 层里，业务规则也不该写进格式校验器。
