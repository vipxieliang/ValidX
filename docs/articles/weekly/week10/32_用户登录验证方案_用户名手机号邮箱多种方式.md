## 概述

几乎每个系统都有登录页，而登录页里最常见的一个输入框叫"**账号**"。同一个框，背后可能是三种完全不同的东西：

| 账号形态 | 示例 | 规则来源 |
|---------|------|---------|
| 用户名 | `zhangsan_2024` | 业务自定义规则 |
| 手机号 | `13812345678` | 国家号码段规范 |
| 邮箱 | `zhangsan@example.com` | RFC 5322 标准 |

注册时，用户明确选择了"用手机号注册"还是"用邮箱注册"，验证器知道自己在验什么；但**登录时系统不知道**——用户可能输用户名，也可能输手机号或邮箱。这就是登录验证与注册验证最本质的差别：**必须先识别账号类型，再按类型精确验证**。

本文用 ValidX 给出一个完整的登录验证方案：识别器 + 分派验证 + 密码校验，覆盖用户名、手机号、邮箱三种登录方式，并讲清楚登录场景与注册场景在密码策略上的关键区别。

## 一、登录验证 ≠ 注册验证

把一次登录请求拆开，它实际经过**三层**：

```
┌─────────────────────────────────────────────┐
│  ① 识别层：这个"账号"是什么类型？            │
│     （用户名 / 手机号 / 邮箱）               │
├─────────────────────────────────────────────┤
│  ② 格式层：格式合法吗？                      │
│     （正则 / ValidX 验证器）                 │
├─────────────────────────────────────────────┤
│  ③ 认证层：这个用户存在吗？密码对吗？        │
│     （查库 + 密码比对）                      │
└─────────────────────────────────────────────┘
```

| 对比项 | 注册验证 | 登录验证 |
|--------|---------|---------|
| 账号类型 | **已知**（表单明确选了） | **未知**（需先识别） |
| 验证强度 | 高（手机号必须精确 11 位） | 中（识别时允许宽松，再精确验证） |
| 失败处理 | 告诉用户"格式不对" | 只告诉"账号或密码错误"（防枚举） |
| 密码策略 | 强校验（长度 + 复杂度） | 只查非空 + 长度下限 |

**关键认知**：注册是"格式优先"，登录是"安全优先"。登录时即使格式不对，也不应该告诉用户"邮箱格式错误"还是"手机号格式错误"——因为这会泄露"该格式的账号是否存在"的信息（详见第七节）。

## 二、账号类型识别：宽松识别，精确验证

### 2.1 识别规则

识别不需要严格验证，只需要"大概率猜中类型"，让后续分派到正确的验证器。规则如下：

| 目标类型 | 识别规则（宽松） | 说明 |
|---------|-----------------|------|
| 邮箱 | `^[^@\s]+@[^@\s]+\.[^@\s]+$` | 包含 `@` 和域名，即可判定为邮箱 |
| 手机号 | `^1[3-9]\d{9}$` | 中国大陆手机号段（13/14/15/16/17/18/19 开头） |
| 用户名 | 其余所有非空输入 | 兜底类型 |

### 2.2 识别顺序与陷阱

识别顺序必须是 **邮箱 → 手机号 → 用户名兜底**，两个原因：

1. **邮箱和用户名不冲突**：用户名通常不允许包含 `@`，所以"含 `@`"是邮箱的可靠信号；
2. **手机号和用户名会冲突**：如果业务允许"纯数字用户名"，一个 11 位纯数字用户名会被手机号规则抢先识别。常见取舍：
   - **注册时禁止纯数字用户名**（推荐）——避免与手机号混淆，也是大多数平台的通行做法；
   - 如果必须允许纯数字用户名，识别时先查库"这个数字是不是已注册的手机号"，成本较高，一般不建议。

### 2.3 识别器实现

```java
import java.util.regex.Pattern;

public enum AccountType {
    USERNAME("用户名"),
    PHONE("手机号"),
    EMAIL("邮箱"),
    UNKNOWN("未知账号类型");

    private final String label;

    AccountType(String label) {
        this.label = label;
    }

    public String getLabel() {
        return label;
    }
}
```

```java
import java.util.regex.Pattern;

public final class AccountTypeDetector {

    // 宽松识别规则：只求"猜中类型"，不负责强验证
    private static final Pattern EMAIL_PATTERN =
            Pattern.compile("^[^@\\s]+@[^@\\s]+\\.[^@\\s]+$");
    private static final Pattern PHONE_PATTERN =
            Pattern.compile("^1[3-9]\\d{9}$");

    private AccountTypeDetector() {
    }

    public static AccountType detect(String account) {
        if (account == null || account.isBlank()) {
            return AccountType.UNKNOWN;
        }
        if (EMAIL_PATTERN.matcher(account).matches()) {
            return AccountType.EMAIL;
        }
        if (PHONE_PATTERN.matcher(account).matches()) {
            return AccountType.PHONE;
        }
        return AccountType.USERNAME;
    }
}
```

> 注意：识别用的正则与验证用的正则**不是同一套**。识别用宽松版（`1[3-9]\d{9}`），验证交给 ValidX 的 `isChinesePhone` 等强验证器——识别器负责"分对类"，验证器负责"把好关"。

## 三、三种账号的验证规则

识别出类型后，分派到对应的 ValidX 验证器：

| 账号类型 | ValidX 验证方法 | 规则说明 |
|---------|----------------|---------|
| 用户名 | `isAlphaDash(account)` | 仅字母、数字、下划线、短横线（`^[a-zA-Z0-9_-]+$`） |
| 用户名 | `isAlphaNumber(account)` | 若业务只允许字母数字，用这个替代 |
| 用户名 | `isChinese(account)` / 自定义 | 若允许中文用户名，配合 `@ChineseAlphaDash` 注解 |
| 手机号 | `isChinesePhone(account)` | 中国大陆手机号（11 位，号码段校验） |
| 手机号 | `isPhoneNumber(account, "+86")` | 国际版：指定国家代码，可配 `strict` 严格模式 |
| 邮箱 | `isEmail(account)` | RFC 5322 规范的邮箱格式 |

链式写法（三个分支各一行）：

```java
ValidX chain = ValidX.init().withLocale(Locale.SIMPLIFIED_CHINESE);

switch (type) {
    case EMAIL    -> chain.isEmail(account);               // 邮箱走 RFC 5322
    case PHONE    -> chain.isChinesePhone(account);        // 手机号走号码段
    case USERNAME -> chain.isAlphaDash(account);           // 用户名走字符集
    default       -> { /* UNKNOWN 已在上游拦截 */ }
}
```

## 四、完整登录验证实现

把识别器与 ValidX 链式验证组合成一个完整的 `LoginValidator`，可运行、可直接接入 Controller：

```java
import io.github.vipxieliang.validx.chain.ValidX;
import io.github.vipxieliang.validx.exception.ValidationException;

import java.util.ArrayList;
import java.util.List;
import java.util.Locale;

public final class LoginValidator {

    private LoginValidator() {
    }

    /**
     * 登录请求校验：识别账号类型 → 格式验证 → 密码基础校验
     *
     * @return 错误列表，为空表示通过
     */
    public static List<String> validate(String account, String password) {
        List<String> errors = new ArrayList<>();

        // ① 识别账号类型
        AccountType type = AccountTypeDetector.detect(account);
        if (type == AccountType.UNKNOWN) {
            errors.add("账号不能为空");
            return errors;   // 空账号直接返回，不进入后续链
        }

        // ② 按类型做格式验证（错误消息自动为中文，含字段标签）
        ValidX chain = ValidX.init()
                .withLocale(Locale.SIMPLIFIED_CHINESE);
        chain.field("账号");
        switch (type) {
            case EMAIL    -> chain.isEmail(account);
            case PHONE    -> chain.isChinesePhone(account);
            case USERNAME -> {
                // 用户名长度限制：ValidX 链负责字符集，长度由业务显式判断
                if (account.length() < 4 || account.length() > 20) {
                    errors.add("用户名长度需在 4-20 位之间");
                }
                chain.isAlphaDash(account);
            }
            default -> { }
        }
        errors.addAll(chain.getErrors());

        // ③ 密码基础校验：登录场景只查"非空 + 长度下限"
        if (password == null || password.length() < 8) {
            errors.add("密码长度不能少于 8 位");
        }
        return errors;
    }
}
```

Controller 中调用：

```java
@PostMapping("/login")
public Result<?> login(@RequestBody LoginRequest request) {
    List<String> errors = LoginValidator.validate(request.getAccount(), request.getPassword());
    if (!errors.isEmpty()) {
        return Result.fail(400, errors);   // 格式错误：返回可读提示
    }
    // 认证层：查库 + 密码比对（见第七节）
    return authService.login(request);
}
```

效果对照：

| 输入账号 | 识别类型 | 验证结果 |
|---------|---------|---------|
| `zhangsan_2024` | 用户名 | 通过（4-20 位 + 字符集合法） |
| `z@`（2 位） | 用户名 | 失败：用户名长度需在 4-20 位之间 |
| `13812345678` | 手机号 | 通过（号码段合法） |
| `1281234567`（10 位） | 用户名 | 失败：`isAlphaDash` 通过但长度不足（业务可优化识别规则） |
| `zhangsan@example.com` | 邮箱 | 通过（RFC 5322） |
| `zhangsan@example` | 用户名 | 失败：不含 `.` 未被识别为邮箱，按用户名验证 → 含 `@` 字符集不合法 |

## 五、注解方式：注册 DTO vs 登录 DTO

登录用链式 API（因为要先识别再分派），但**注册场景类型明确，用注解更简洁**。两种方式在 ValidX 中都能用：

### 5.1 注册 DTO：类型明确，强验证

```java
public class RegisterRequest {

    @NotBlank(message = "账号不能为空")
    private String account;

    @Email(message = "邮箱格式不正确")
    private String email;

    @ChinesePhone(message = "手机号格式不正确")
    private String phone;

    @Password(minLength = 8, requireSpecialChar = true,
              message = "密码至少 8 位，且包含大小写字母、数字和特殊字符")
    private String password;

    // getter / setter 省略
}
```

### 5.2 登录 DTO：只做必填，格式交给 Service 层

```java
public class LoginRequest {

    @NotBlank(message = "账号不能为空")
    private String account;

    @NotBlank(message = "密码不能为空")
    private String password;

    // getter / setter 省略
}
```

**为什么登录 DTO 不用 `@Email` / `@ChinesePhone` 注解？** 因为登录请求里账号类型未知，如果 DTO 上用 `@Email`，手机号登录就永远无法通过——注解是"固定一种类型"，链式 API 才能"先识别再分派"。这也解释了为什么登录验证适合链式、注册验证适合注解。

## 六、密码验证的两个层次

登录和注册对密码的要求完全不同，**混用是常见 bug**：

| 场景 | 校验内容 | ValidX 用法 |
|------|---------|------------|
| 注册 / 重置密码 | 非空 + 长度 + 大小写 + 数字 + 特殊字符 | `isPassword(value, 8)`（默认四要素全开） |
| 登录 | 只查非空 + 长度下限 | 原生判断 `password.length() < 8` |

**为什么登录不能用 `isPassword(value, 8)`？** 看 ValidX 源码（`chain/ValidX.java` 第 821 行）：`isPassword(value, minLength)` 内部调用的是

```java
validatePassword(value, minLength, true, true, true, true, errors, getLocale());
```

四个 `true` 表示大小写字母、数字、特殊字符**全部必查**。这是注册场景的强度校验。如果登录时用同一套规则，历史上注册过弱密码的老用户将**永远无法登录**——登录校验的目的不是"督促用户设强密码"，而是"别让请求带着空密码进认证层"。

注册时强度校验（正确姿势）：

```java
ValidX chain = ValidX.init()
        .withLocale(Locale.SIMPLIFIED_CHINESE)
        .field("密码")
        .isPassword(password, 8);   // 8 位 + 四要素

if (!chain.passed()) {
    throw new ValidationException(chain.getErrors());
}
```

另外提醒：验证只解决"格式"，不解决"存储"。密码必须用 BCrypt 等不可逆算法加盐存储，**绝不能存明文或 MD5**——那是另一篇文章的主题。

## 七、安全注意点

登录验证踩坑最多的不是格式，而是**信息泄露**：

### 7.1 统一错误消息，防用户枚举

格式层失败和认证层失败，**对用户要说一样的话**：

```java
// ❌ 错误：泄露了"该手机号未注册"
if (user == null) {
    return Result.fail("该手机号未注册");
}
if (!passwordEncoder.matches(rawPwd, user.getPassword())) {
    return Result.fail("密码错误");
}

// ✅ 正确：无论哪一步失败，统一返回
if (user == null || !passwordEncoder.matches(rawPwd, user.getPassword())) {
    return Result.fail("账号或密码错误");
}
```

不然外部探测方可以批量试号，从"该手机号未注册"和"密码错误"的差异中**枚举出哪些手机号注册过**。

### 7.2 格式失败与认证失败分通道记录

- 格式失败（`LoginValidator` 返回错误）：正常业务噪音，记 debug 日志；
- 认证失败（查库 + 密码比对失败）：安全事件，记 warn 日志，**计入失败次数**，触发限流或验证码；
- 密码比对本身要恒定时间比较，防时序侧信道。

### 7.3 三重防线

| 防线 | 手段 |
|------|------|
| 格式层 | ValidX 识别 + 验证，挡掉畸形输入 |
| 频率层 | IP / 账号维度失败次数限制，触发验证码 |
| 认证层 | 密码哈希比对 + 统一错误消息 |

## 八、国际化

同一套验证逻辑，切换 `Locale` 即可输出不同语言——登录接口对全球用户友好：

```java
// 中文用户
ValidX zh = ValidX.init().withLocale(Locale.SIMPLIFIED_CHINESE)
        .field("Account").isEmail(account);

// 英文用户
ValidX en = ValidX.init().withLocale(Locale.ENGLISH)
        .field("Account").isEmail(account);
```

`field()` 里的标签也可以按语言切换：

```java
String label = locale.equals(Locale.SIMPLIFIED_CHINESE) ? "账号" : "Account";
```

## 总结

登录验证与注册验证最大的不同，是一个"**账号输入框**"背后承载了三种身份形态。完整的登录验证方案可以归纳为一条流水线：

```
识别类型（宽松） → 分派验证（精确） → 密码下限（宽松） → 统一错误（防枚举）
```

四个环节里三个"宽松"、一个"精确"，这不是矛盾，而是分层：

- **识别宽松**：只求分类正确，交给后续强验证兜底；
- **验证精确**：`isEmail` / `isChinesePhone` / `isAlphaDash` 各司其职；
- **密码宽松**：登录只查非空与长度下限，强密码策略只属于注册/重置；
- **错误统一**：对用户永远只说"账号或密码错误"。

这套方案与系列其他文章相互衔接：注册链路可参考《订单数据验证：从购物车到支付的完整验证链路》（week09）中的分层思想；邮箱与固定电话的深度验证规则，将在第 11 周《邮箱验证的正确姿势：RFC 5322 标准与实战》和《固定电话验证详解》中展开。
