## 引言

"请填写您的 QQ 号""微信号一经填写不可随意修改，请谨慎输入"——用户资料页、抽奖登记表、客服工单、第三方账号绑定，社交账号字段几乎出现在所有 To C 系统里。

这类字段看似简单，实际却常被写错：有人拿校验手机号的正则去套 QQ 号（漏掉超短号），有人允许微信号里填中文（用户根本设不了这种号），更常见的是既不拦格式、也不拦空格，脏数据一路灌进库里，到运营导出联系方式时才发现一半是废号。

ValidX 从 v1.0.0 起内置了两个专门的社交账号验证器：

- **`@QQ`**（链式 `isQQ`）：校验 QQ 号——纯数字、首位非 0、长度 ≥ 5 位
- **`@WeChat`**（链式 `isWeChat`）：校验微信号——字母开头、6~20 位字母/数字/下划线/减号、不支持中文

本文对照 `QQValidator` / `WeChatValidator` 源码与单元测试，讲清两条格式规则的完整边界、空值语义，以及"格式合法 ≠ 账号存在"这个社交账号校验最重要也最容易被误解的前提。

> 文中结论对照 ValidX v1.2.0 源码与单元测试核实。

## 一、社交账号验证的特殊性：格式 ≠ 存在性

社交账号验证和身份证、银行卡这类"有校验位算法"的号码有本质区别：

| 维度 | 身份证 / 银行卡 | QQ 号 / 微信号 |
|------|----------------|---------------|
| 校验位 | 有（GB 11643 加权、Luhn） | **无任何校验位** |
| 分配方 | 国家标准，结构全国统一 | 平台自主分配，规则可随运营调整 |
| 格式校验能证明的 | "结构合法，大概率是真号" | **"格式上像个号，仅此而已"** |
| 存在性验证 | 无法本地验证 | 需调平台开放接口（通常无公开渠道） |

QQ 号和微信号都是**腾讯自主分配的私有命名空间**：位数范围、起始规则由腾讯的运营策略决定，历史上都在变化。任何本地校验都只能做"格式层"的过滤：

1. **拦住明显的脏数据**——空格、中文、特殊字符、超短输入；
2. **拦住结构错误**——QQ 号以 0 开头、微信号数字开头等；
3. **无法证明账号真实存在**——`123456789` 格式完全合法，但可能早已注销或从未注册。

所以正确的心智模型是：`@QQ` / `@WeChat` 是**入口过滤**，负责把明显不合法的输入挡在业务流程之外；至于账号是否真实、是否属于当前用户，那是风控和实名验证（短信验证、平台开放接口）的职责。

## 二、API 总览：注解与链式双入口

与 ValidX 全部规则一致，两个验证器都有注解、链式两条等价入口：

```java
// 注解方式
public class UserProfileDTO {
    @QQ
    private String qq;        // "10000"、"123456789" 通过

    @WeChat
    private String wechatId;  // "wechat_id_2024" 通过
}

// 链式方式
ValidX validator = ValidX.init();
validator.isQQ("10000");       // true
validator.isWeChat("a12345"); // true
```

| 规则 | 注解 | 链式方法 | 验证器位置 | 引入版本 |
|------|------|---------|-----------|---------|
| QQ 号 | `@QQ` | `isQQ(Object value)` | `validator.china.QQValidator` | v1.0.0（2025/10） |
| 微信号 | `@WeChat` | `isWeChat(Object value)` | `validator.network.WeChatValidator` | v1.0.0（2025/10） |

默认错误消息（中文，另有 9 种语言的翻译）：

- `@QQ`：`无效的QQ号`（消息键 `io.github.vipxieliang.validx.annotation.qq`）
- `@WeChat`：`微信格式不正确`（消息键 `io.github.vipxieliang.validx.annotation.wechat`）

两者都是无参数注解——格式规则由验证器内建，没有可选属性；如需自定义边界（例如限制 QQ 号最长 11 位），见 3.2 节的组合用法。

## 三、QQ 号格式规则详解

### 3.1 正则拆解

`QQValidator` 的全部核心逻辑就一行正则：

```java
return value.matches("^[1-9][0-9]{4,}$");
```

拆开看是三条硬规则：

| 规则 | 正则片段 | 含义 |
|------|---------|------|
| 首位非 0 | `[1-9]` | QQ 号从 1~9 开头，`01234` 非法 |
| 其余纯数字 | `[0-9]{4,}` | 后面至少再跟 4 位数字 |
| 有下限无上限 | `{4,}` | 总长度 **≥ 5 位**，**不设上限** |

对照官方测试用例：

```java
validator.isQQ("10000");      // true：5 位，最短合法长度（腾讯早期号段）
validator.isQQ("123456789");  // true：9 位，常见量级

validator.isQQ("1234");       // false：只有 4 位，太短
validator.isQQ("01234");      // false：以 0 开头
validator.isQQ("12345a");     // false：含字母
```

三个设计细节值得注意：

1. **`10000` 能通过**。腾讯最早的五位号段（如 10000 段的早期号）是真实存在的，把下限定在 5 位正是为了兼容这类存量号；写成 `{5,}` 之外的"6 位起步"会把老号误杀。
2. **字符集用 `[0-9]` 而非 `\d`**，配合 `matches()` 的默认语义，**全角数字（`１２３４５`）会被拒绝**——它们不是 ASCII 数字。这对从 IME 输入法、Excel 复制粘贴来的数据是一道有效拦截。
3. **不 trim 空格**。`" 12345"`（带前导空格）会直接失败而不是被宽容处理——空格本身就是脏数据信号，是否清理是上游 `trim()` 的决定，验证器不做隐式修改。

### 3.2 与真实 QQ 规则的对齐与收窄建议

腾讯当前实际分配的 QQ 号大约在 5~11 位之间，但这个范围由运营决定，**不是公开稳定的标准**。ValidX 选择只设下限（5 位）、不设上限，宁可宽松也不误杀——未来号段扩到 12 位时，库不用发版。

如果你的业务需要更紧的边界（例如明确只收当前真实号段），可以叠加标准注解组合收窄：

```java
public class ContactInfoDTO {

    // 收窄为 5~11 位：@QQ 管格式，@Size 管长度上限
    @QQ
    @Size(max = 11, message = "QQ号长度应在5~11位之间")
    private String qq;
}
```

注意顺序无所谓——Bean Validation 会把两个约束都跑一遍，任一失败都会产生各自的违规消息。

## 四、微信号格式规则详解

### 4.1 正则拆解

`WeChatValidator` 用的是预编译的静态 `Pattern`：

```java
private static final Pattern WECHAT_PATTERN =
        Pattern.compile("^[a-zA-Z][a-zA-Z\\d_-]{5,19}$");
```

对应微信官方的微信号设置规则，四条：

| 规则 | 正则片段 | 含义 |
|------|---------|------|
| 字母开头 | `^[a-zA-Z]` | 必须以英文字母开头（大小写均可） |
| 允许字符集 | `[a-zA-Z\d_-]` | 字母、数字、下划线、减号 |
| 长度 6~20 | `[...]{5,19}` | 首字母 + 5~19 位 = **总长 6~20 位** |
| 不支持中文 | 字符集不含 CJK | `测试账号` 非法 |

对照官方测试用例：

```java
validator.isWeChat("abcdef");                // true：最短 6 位
validator.isWeChat("a12345");                // true：字母开头 + 数字
validator.isWeChat("Test_User-123");         // true：下划线、减号
validator.isWeChat("WeChatID_2024");        // true：大小写混合
validator.isWeChat("a1234567890123456789");  // true：最长 20 位

validator.isWeChat("12345");                // false：数字开头
validator.isWeChat("abc");                  // false：太短（不足 6 位）
validator.isWeChat("a123456789012345678901"); // false：太长（超过 20 位）
validator.isWeChat("_abcdef");              // false：下划线开头
validator.isWeChat("-abcdef");              // false：减号开头
validator.isWeChat("测试账号");              // false：中文
validator.isWeChat("test@user");            // false：@ 非法
```

一个容易算错的地方是**长度边界**：正则写的是 `{5,19}`，但加上开头的 `[a-zA-Z]`，实际总长度是 **6~20 位**。这与微信客户端"6-20个字母、数字、下划线和减号"的官方口径一致，写正则时别把首字符漏在长度统计外。

### 4.2 微信号 ≠ 微信登录账号

业务建模时要分清两个概念，`@WeChat` 校验的是前者：

| 概念 | 是什么 | 格式 |
|------|--------|------|
| **微信号** | 用户自己设置的账号名（唯一，一年可改一次） | 字母开头，6~20 位，`@WeChat` 校验的对象 |
| 微信登录账号 | 手机号 或 QQ 号（用于登录） | 纯数字，`@WeChat` **不**接受 |

所以如果产品需求是"填写微信登录方式"，收集到的可能是手机号或 QQ 号，这时应该用 `@ChinesePhone` / `@QQ` 分别校验或做"多选一"组合，而不是 `@WeChat` 一把梭——`13800138000` 会因数字开头被 `@WeChat` 拒绝，但它恰恰是合法的微信登录账号。

## 五、注解方式实战

### 5.1 基础用法

```java
public class UserProfileDTO {

    @QQ(message = "QQ号格式不正确")
    private String qq;

    @WeChat(message = "微信号格式不正确")
    private String wechatId;
}
```

### 5.2 必填 + 格式：判空注解别忘了

`@QQ` / `@WeChat` 与 ValidX 全部格式注解一致，对 `null` / `""` **放行**（见第七节）。必填场景必须叠加判空注解：

```java
public class LotteryEntryDTO {

    // 必填且格式正确
    @NotBlank(message = "QQ号不能为空")
    @QQ
    private String qq;

    // 可选字段：填了才校验格式
    @WeChat
    private String wechatId;
}
```

可选字段是这套"放行空值"设计最大的受益者：用户不填微信号完全合法，填了才校验格式——不需要为"可空但非空时必须合法"写任何 if 判断。

### 5.3 组合收窄

```java
public class BindingForm {

    @QQ
    @Size(max = 11, message = "QQ号超出常见号段长度")
    private String qq;

    @WeChat
    @Size(min = 6, max = 20, message = "微信号长度应为6~20位")
    private String wechatId;   // 长度双保险，格式由 @WeChat 负责
}
```

## 六、链式方式实战

链式入口适合 Service 层动态校验（表单引擎、接口防脏数据等）：

```java
public void validateContact(String qq, String wechatId) {
    ValidX validator = ValidX.init()
            .config(ValidXConfig.GLOBAL_NOT_EMPTY)   // 全局必填
            .field("QQ号").isQQ(qq)
            .field("微信号").isWeChat(wechatId);

    if (!validator.passed()) {
        throw new ValidationException(validator.getErrors());
        // 错误消息形如："QQ号: 无效的QQ号"
    }
}
```

`field("...")` 的字段标签会拼进错误消息，报错时用户能直接看到是哪个字段错了。

可选字段用局部豁免：

```java
ValidX validator = ValidX.init()
        .config(ValidXConfig.GLOBAL_NOT_NULL)
        .field("QQ号").isQQ(qq)                      // 必填
        .field("微信号").allowNull().isWeChat(wechatId); // 可选：null 放行，非空则校验格式
```

多账号混合校验（来自官方测试风格）：

```java
ValidX validator = ValidX.init()
        .isQQ("10000")
        .isQQ("123456789")
        .isWeChat("a12345");

validator.passed();  // true
```

## 七、空值与判空语义

两个验证器的空值处理完全一致，与 ValidX 全线注解对齐：

| 输入 | `@QQ` / `isQQ` | `@WeChat` / `isWeChat` | 说明 |
|------|:---:|:---:|------|
| `null` | 通过（true） | 通过（true） | 判空交给 `@NotNull` |
| `""` | 通过（true） | 通过（true） | 判空交给 `@NotBlank` / `@NotEmpty` |
| 非 String 类型 | 失败 | 失败 | 链式传 `Object`，非字符串直接判失败 |
| 合法格式字符串 | 通过 | 通过 | 见上文规则 |

源码层面两者都是开头一句放行：

```java
if (value == null || value.isEmpty()) {
    return true; // 空值处理交给@NotNull等其他注解处理
}
```

链式模式下受全局/局部配置影响：`GLOBAL_NOT_NULL` / `GLOBAL_NOT_EMPTY` 会让对应空值失败，`allowNull()` / `allowEmpty()` 可逐字段豁免——与 `@Duration` 等其他规则的行为完全一致。

## 八、常见有效/无效对照表

| 输入 | `@QQ` | `@WeChat` | 失败原因 |
|------|:---:|:---:|---------|
| `10000` | ✅ | ❌ | 微信号不接受纯数字（数字开头） |
| `123456789` | ✅ | ❌ | 同上 |
| `1234` | ❌ | ❌ | QQ 不足 5 位；微信不足 6 位 |
| `01234` | ❌ | ❌ | QQ 以 0 开头 |
| `12345a` | ❌ | ❌ | QQ 含字母；微信数字开头 |
| `abcdef` | ❌ | ✅ | QQ 是纯字母，非纯数字 |
| `a12345` | ❌ | ✅ | 同上 |
| `Test_User-123` | ❌ | ✅ | — |
| `a1234567890123456789`（20 位） | ❌ | ✅ | QQ 无上限所以长度没问题，但含字母 ❌；微信正好 20 位 ✅ |
| `a123456789012345678901`（22 位） | ❌ | ❌ | 微信超 20 位 |
| `_abcdef` / `-abcdef` | ❌ | ❌ | 微信必须字母开头 |
| `测试账号` | ❌ | ❌ | 微信不支持中文；QQ 非纯数字 |
| `test@user` | ❌ | ❌ | `@` 不在允许字符集 |
| `１２３４５`（全角数字） | ❌ | ❌ | 非 ASCII 数字，直接拒绝 |
| `" 12345"`（带空格） | ❌ | ❌ | 不做 trim，空格即非法 |
| `null` / `""` | ✅ | ✅ | 放行，判空归 `@NotNull` / `@NotBlank` 管 |

> 注意 `abcdef` 这一行：**它对 `@WeChat` 合法、对 `@QQ` 非法**；而 `10000` 恰好相反。两个验证器的规则域几乎不重叠，选错验证器 = 全量误判，这也是"不要拿一个正则通吃社交账号"的原因。

## 九、典型业务场景

| 场景 | 推荐组合 | 说明 |
|------|---------|------|
| 用户资料页 - 联系方式 | `@QQ` + `@WeChat`（均可选） | 可选字段：不填放行，填了才校验 |
| 抽奖/活动登记 | `@NotBlank` + `@QQ` | 必填 QQ 号，用于发奖联系 |
| 客服工单系统 | `@WeChat` + `@Size(max=20)` | 微信号回访渠道，长度双保险 |
| 第三方账号绑定 | `@QQ` / `@WeChat` + 业务层"多选一" | 常见需求"手机号或微信至少填一个"，注解层各自校验格式，二选一逻辑放 Service 或 ClassLevel 约束 |
| 数据清洗/导入 | 链式 `isQQ` / `isWeChat` 批量过滤 | 导 Excel 前批量校验，脏行进错误报告 |

其中"手机号或微信二选一"这类**跨字段条件校验**超出单字段注解的表达能力，ValidX 规划中的 `@AnyOf`（ClassLevel 约束）就是为它准备的；当前版本建议在 Service 层组合单字段校验 + 一行业务判断实现。

## 十、容易忽略的实现细节与坑

1. **格式合法 ≠ 账号存在**。`@QQ` / `@WeChat` 只做格式层过滤；账号真实性、归属（是否本人）需短信验证码或平台开放接口确认。所有"格式校验通过就入库发奖"的流程都缺一道风控。
2. **微信号≠微信登录账号**。登录账号可能是手机号或 QQ 号，`@WeChat` 会拒绝纯数字输入——收"登录方式"的字段别用 `@WeChat`（见 4.2）。
3. **QQ 号没有长度上限**。正则是 `[0-9]{4,}`，对齐"下限 5 位、不误杀未来号段"的策略；需要收窄就叠 `@Size(max=11)`。反过来，**别指望它帮你拦超长攻击串**——拦截超长输入是 `@Size` / 全局长度限制的职责。
4. **全角数字会被拒**。`１２３４５` 不通过——字符集是 ASCII `[0-9]`。从 Excel、输入法全角模式复制的数据常踩这个坑；要么让用户重输，要么上游显式 `Normalizer` 转半角后再校验。
5. **不做 trim**。`" 12345"` 直接失败。这是有意设计：验证器不隐式修改输入。如果产品上希望宽容，应在 Controller 层统一 `trim()`，而不是每个验证器各管各的。
6. **正则编译的写法不同**。`QQValidator` 用 `value.matches(...)`（每次调用重新编译正则），`WeChatValidator` 用静态预编译 `Pattern`。日常量级两者都无感知；若在高频热路径（如清洗百万行数据）里跑 QQ 校验，可以预编译同样的正则替换，语义不变。
7. **微信号区分大小写吗？** 正则层面 `abc123` 与 `ABC123` 都合法；微信实际语义里两者是否视为同一账号由平台决定，校验层不介入。如需统一，入库前自行 `toLowerCase()`。
8. **判空分离是特性不是 bug**。`null` / `""` 放行 + `@NotBlank` 兜底，让"可空但非空必须合法"的字段零成本实现；忘记加 `@NotBlank` 则必填字段会被空值穿透——这是使用所有 ValidX 格式注解的共同注意点。
9. **别用一个大正则通吃**。`"^(\\d{5,}|[a-zA-Z]\\w{5,19})$"` 这种"QQ或微信"混合校验看似省事，实际会让错误提示失去指向性（用户不知道自己哪个字段该长什么样），也让第 4.2 节的概念混淆更严重。分字段、分注解。

---

## 总结

| 主题 | 结论 |
|------|------|
| 定位 | 社交账号校验 = 格式层过滤，不证明账号存在 |
| `@QQ` 规则 | `^[1-9][0-9]{4,}$`：首位非 0、纯数字、总长 ≥5 位、无上限 |
| `@WeChat` 规则 | `^[a-zA-Z][a-zA-Z\d_-]{5,19}$`：字母开头、总长 6~20、字母/数字/`_`/`-`、无中文 |
| API | 注解 `@QQ` / `@WeChat` + 链式 `isQQ` / `isWeChat` |
| 空值 | `null` / `""` 放行，必填叠加 `@NotBlank` 或全局非空配置 |
| 收窄手段 | 叠加 `@Size` 限制长度上下限，与格式校验正交组合 |
| 最易踩的坑 | ①拿 `@WeChat` 校验"微信登录账号"（可能是手机号/QQ）；②忘了全角数字/空格不被宽容处理 |

QQ 号与微信号的格式规则本身简单，真正的工程价值在于：**把"格式过滤"与"存在性/归属验证"清晰分层**——前者交给 `@QQ` / `@WeChat` 一行声明，后者留给风控与验证码流程。分清这两层，社交账号字段就不会再变成脏数据重灾区。
