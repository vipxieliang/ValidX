## 引言

"用户改了昵称，但邮箱、手机、生日都没动"——用户中心的**修改接口**几乎都是这种**部分更新**（Partial Update）场景：客户端只提交需要修改的字段，其余字段保持原值不动。

部分更新验证的难点不在"某个字段怎么校验"，而在于**校验范围的动态性**：

- 新增（Create）时：邮箱、手机必填且格式正确；
- 修改（Update）时：只有提交了的字段才需要校验，没提交的字段既不能报"必填缺失"，也不能校验它的旧值；
- 更细一层：客户端传 `email: null` 是想**清空**还是**没传**？传 `""` 又算什么？

> 文中结论对照 ValidX v1.2.0 源码与 README「部分更新」官方示例核实，注解/链式方法名均真实存在。

ValidX 的**判空与格式分离**设计（所有格式验证器对 `null`/`""` 默认放行）恰好为部分更新提供了天然底座——格式验证只管"有值的时候格式对不对"，至于"这个字段这次要不要校验"，由调用方通过三种策略控制。本文逐一拆解。

## 一、部分更新的本质：先分清"四种状态"

先看客户端能提交的四种情况（以 JSON 反序列化到 `Map` 为例）：

| 状态 | 请求体示例 | `containsKey` | `map.get()` | 业务意图 |
|------|-----------|--------------|-------------|---------|
| 字段缺失 | `{"email":"a@b.com"}`（无 phone） | `false` | — | **不更新** phone，沿用旧值 |
| 显式 null | `{"email":null}` | `true` | `null` | **清空**？还是非法？业务定义 |
| 空字符串 | `{"email":""}` | `true` | `""` | 想"清空"或"误传"，业务定义 |
| 有值 | `{"email":"new@b.com"}` | `true` | 值 | **更新**为指定值 |

而 ValidX 的格式验证器（`isEmail`、`isChinesePhone`、`@Email`…）对 `null` 和 `""` **一律放行**——这是设计而非缺陷：格式验证器回答的是"有值时格式是否正确"。

于是部分更新有了两种截然不同的组织方式：

1. **方案一（Map 型）**：用 `containsKey` 决定"这个字段这次要不要校验"——适合 REST `PATCH`，语义最精确；
2. **方案二/三（DTO 型）**：把"未更新 = null"约定好，让格式验证器对 null 放行的默认行为替你跳过——代码最简洁。

两种方式的取舍贯穿全文。

## 二、方案一：Map 型 PATCH，containsKey 只校验提交字段

RESTful 接口中，`PATCH /api/users/{id}` 通常用 `Map<String, Object>` 接收**部分字段**。README 给出了这一模式的雏形：只验证更新 Map 中存在的字段。

把它补全成可直接落地的版本：

```java
public void updateUserProfile(String userId, Map<String, Object> updates) {
    ValidX validator = ValidX.init();  // 默认：null/空字符串放行

    // email 属于账号标识，提交了就要求非空且格式正确（不允许清空）
    if (updates.containsKey("email")) {
        validator.field("邮箱").notEmpty().isEmail(updates.get("email"));
    }

    // 手机号同上：提交了就必须有效
    if (updates.containsKey("phone")) {
        validator.field("手机号").notEmpty().isChinesePhone(updates.get("phone"));
    }

    // 生日：允许显式传 null/"" 表示清空，但只要有值就校验格式 + 必须是过去日期
    if (updates.containsKey("birthday")) {
        Object birthday = updates.get("birthday");
        validator.field("生日").isDate(birthday);              // 有值时格式必须正确
        if (birthday != null && !birthday.toString().isEmpty()) {
            validator.field("生日").isPastDate(birthday);      // 必须是过去日期
        }
    }

    // 个人主页：可选，允许清空
    if (updates.containsKey("website")) {
        validator.field("个人主页").isUrl(updates.get("website"));
    }

    if (!validator.passed()) {
        throw new ValidationException(validator.getErrors());
    }

    // ... 通过后按字段生成动态 UPDATE SQL / 逐个 set
    // UPDATE user SET email=?, phone=? WHERE id=?  （只拼提交了的字段）
}
```

三个关键细节：

1. **`containsKey` 是这道方案的灵魂**：字段缺失（`false`）时连校验方法都不调用——未更新字段既不会触发"必填缺失"，也不会拿旧值去校验。这是 DTO 全量校验做不到的。
2. **`notEmpty()` 表达"不允许清空"**：`email` 若传 `""`，默认会放行入库变成空串。加上 `notEmpty()` 后，`null` 和 `""` 都被拒——语义变成"提交了 email 就必须是有效值"。要不要 `notEmpty`，取决于该字段**是否允许清空**的业务规则。
3. **`.field("标签")` 让错误定位到字段**：`getErrors()` 的错误消息里会带上中文标签，而不是 `Map` 的 key。

## 三、方案二：DTO 型 PATCH，null 即不更新

很多团队不喜欢 `Map`，倾向用 DTO。此时约定一个核心规则：**UpdateDTO 中 `null` = 该字段本次不更新**（框架层做部分更新时用 `BeanUtils` 拷贝非空属性或动态 SQL 拼接）。

一旦立下这个约定，校验代码可以极度简洁——因为格式验证器对 `null` 默认放行：

```java
public class UserUpdateDTO {
    private String email;
    private String phone;
    private String birthday;
    private String website;
    // getter / setter 省略
}

public void updateUserProfile(Long userId, UserUpdateDTO dto) {
    ValidX validator = ValidX.init();  // 默认 DEFAULT：null/"" 放行 = "未更新字段自动跳过"

    // 字段为 null 时，以下方法全部自动放行，无需逐个 if
    validator.field("邮箱").notEmpty().isEmail(dto.getEmail())          // email：更新时必须非空
             .field("手机号").notEmpty().isChinesePhone(dto.getPhone()) // phone：更新时必须非空
             .field("生日").isDate(dto.getBirthday())                   // 生日：null=不更新，有值则校验
             .field("个人主页").isUrl(dto.getWebsite());                // 主页：null=不更新

    if (!validator.passed()) {
        throw new ValidationException(validator.getErrors());
    }
}
```

对比方案一，这里不需要任何 `if`：DTO 里没动的字段是 `null`，链式校验自动跳过；动了且有值的字段，格式校验照常执行。

**代价是语义被压扁了**：DTO 模式下 `null` 同时承载"未更新"与"想清空"两种意图。如果业务允许把 website 清空，客户端就只能传 `""` 而不是 `null`（`""` 对格式验证器同样放行，但对 DB 写入是"清空为 `''`"还是"置为 NULL"要自己定）。所以方案二适合**简单规则：可空的普通字段只能留旧值或换新值，不能置空**。

> 注意局部状态是**每次验证方法调用后自动重置**的：上面 `.notEmpty()` 只作用于紧跟它的 `email`，不会"污染"后面的 `birthday`/`website`。这正是部分更新场景能放心混写"必填类 + 可选类"字段的前提。

## 四、方案三：注解方式，UpdateDTO 与 CreateDTO 分离

Controller 层注解验证（`@Valid`）是声明式首选，但**必须新建独立的 UpdateDTO**，不能复用注册 DTO：

```java
// ❌ 错误示范：新增用的 DTO 直接拿去接收 PATCH
public class UserRegisterDTO {
    @NotBlank(message = "邮箱不能为空")
    @Email
    private String email;   // PATCH 只改生日时，email 是 null → 直接报"邮箱不能为空"
}

// ✅ 正确：UpdateDTO 只放格式注解，不放大必填注解
public class UserUpdateDTO {

    // 判空与格式分离：没有 @NotBlank/@NotNull，
    // null = 不更新，格式注解对 null/"" 自动放行
    @Email
    private String email;

    @ChinesePhone
    private String phone;

    @PastDate            // 生日：过去日期（有值时）
    private String birthday;

    @Enum(target = Gender.class, field = "code")
    private Integer gender;   // 性别：只允许枚举里的值

    // getter / setter 省略
}

@PatchMapping("/users/{id}")
public Result<Void> updateUser(@PathVariable Long id,
                               @Valid @RequestBody UserUpdateDTO dto) {
    // 只有提交且非 null 的字段才会真正走到格式校验
    userService.partialUpdate(id, dto);
    return Result.ok();
}
```

三个要点：

1. **格式注解默认"可选"**：`@Email` 对 `null` 放行，未更新的字段天然通过。这正对应第 12 周 FAQ 里的坑 1——"格式注解拦不住空值"，在这里**反而是特性**。
2. **UpdateDTO 严禁加 `@NotBlank`**：一旦加上，`null`（未更新）就被当成必填缺失拒绝，接口就废了。若个别字段业务上"提交了就不允许空串"（如 email），应改用**方案一 + `notEmpty()`** 表达，因为注解层区分不了"没传"和"传了 `""`"。
3. **Create 与 Update 各建一个 DTO**：注册用 `@NotBlank + @Email`，修改用 `@Email`。规则差异通过 DTO 结构差异表达，最直白、也最好维护。

> 进阶：若两个 DTO 字段太多，可抽公共基类 + 用 Bean Validation 标准 `groups()` 区分（ValidX 注解均实现 `groups` 属性，见任务 7《分组验证详解》，本文不展开）。

## 五、进阶辨析：不更新、清空、赋值三种意图的区分

方案二、三把 `null` 与"不更新"绑定后，会遇到一个真实业务难题：**如何让客户端表达"把这个字段清空"？**

推荐按"字段是否允许置空"分两类约定（写进接口文档）：

| 字段类型 | 允许清空？ | 客户端表达 | 服务端处理 |
|---------|-----------|-----------|-----------|
| 账号标识（email、phone、身份证） | 否 | 只能传新值或缺失 | 提交了就必须 `notEmpty()` + 格式校验 |
| 普通资料（昵称、头像、主页、生日） | 是 | 传 `""` 表示清空 | 格式注解放行 `""`，DB 写入空串或 NULL |

实现时，方案一（Map）能精确处理：`containsKey("website") && 值为空串` 时执行 `UPDATE user SET website = NULL`。

```java
// 清空与不更新的精确分流（Map 型）
if (updates.containsKey("website")) {
    Object website = updates.get("website");
    if (website == null || website.toString().isEmpty()) {
        // 意图：清空个人主页 → SET website = NULL
        sqlBuilder.setNull("website");
    } else {
        validator.field("个人主页").isUrl(website);   // 有值才校验格式
        sqlBuilder.set("website", website);
    }
}
```

至于"显式传 `null`"，**建议直接当非法或清空处理并文档化**——Java/JSON 生态里 `null` 与缺失的区分依赖反序列化器（Jackson 默认把 JSON `null` 放进 Map 的 value），传输链路一换（如某些前端框架会丢弃 null key）语义就不可靠了。能用 `""` 表达的清空就别依赖 `null`。

## 六、特殊字段组合：生日、性别、主页的部分更新

### 6.1 生日：格式 + 语义要叠加

生日属于"有值必须校验、没值自动跳过"的典型字段。链式写法（注意 `isPastDate` 的三档重载：`isPastDate(value)`、`(value, includeToday)`、`(value, includeToday, pattern)`，**没有**"值+pattern"两参版本）：

```java
validator.field("生日").isDate(birthday)         // 1. 必须是合法日期（严格日历，见第 30 篇）
         .field("生日").isPastDate(birthday);    // 2. 必须是过去日期（null 自动放行）
```

⚠️ **陷阱提示**：`@PastDate`/`PastDateValidator` 未启用 `ResolverStyle.STRICT`，走 SMART 解析——生日填 `1990-02-30` 会被**静默归一化**成 `1990-02-28` 后放行（不像 `@Date` 严格模式直接拒绝）。部分更新接口里尤其要小心这种"悄悄改数据"，详情见本站第 30 篇《闰年处理与日期有效性》。若需严格校验请先用 `isDate`/`@Date` 把关。

### 6.2 性别：枚举白名单

性别/国家等字段的修改，用枚举验证比"任意字符串"安全得多：

```java
public enum Gender {
    MALE(1), FEMALE(2);
    private final int code;
    // 构造器、getter 省略
}

// 注解方式：@Enum(target = Gender.class, field = "code")  // UpdateDTO 中，null 放行
// 链式方式：
validator.field("性别").isEnum(genderValue, Gender.class, "code");
```

`gender` 为 `null`（未更新）时自动放行；传了 `3` 这类非法 code 才会报错。

### 6.3 主页/头像 URL

可选字段 + 只校验格式，默认语义即满足：

```java
validator.field("个人主页").isUrl(website);   // null/"" 放行，有值必须合法 URL
```

## 七、易错点速查表

| # | 坑 | 后果 | 正确姿势 |
|---|----|------|---------|
| 1 | 复用新增 DTO 接收 PATCH | 未更新的字段报"必填缺失" | 独立的 UpdateDTO，只放格式注解 |
| 2 | UpdateDTO 上加了 `@NotBlank` | 部分更新永远过不了 | 判空与格式分离；`@NotBlank` 只属于 CreateDTO |
| 3 | 用 Map 却拿 `get(key) != null` 判断"传没传" | 传 `email:null` 被误判为未传 | 用 `containsKey`，再判 value 语义 |
| 4 | 以为格式注解/方法会拦空值，没处理"传了 `""`" | 空串悄悄入库 | 允许清空的字段显式处理 `""`；不允许的加 `notEmpty()` |
| 5 | 忘了 `@Valid` | 注解校验静默不执行 | Controller 参数加 `@Valid`（见 FAQ 坑 8） |
| 6 | `notEmpty()` 写在链中段，担心影响后续字段 | 误解状态作用域 | 局部状态每次校验后自动重置，只作用于紧跟的一个方法 |
| 7 | 把 `null` 当"清空"而前端框架丢弃了 null key | 想清空的字段没被更新 | 用 `""` 表达清空，`null` 语义写进接口文档 |
| 8 | 生日校验只写 `@PastDate` | `1990-02-30` 被静默改成 2/28 | 先 `@Date`/`isDate` 严格把关，再判过去（见第 30 篇） |

## 八、综合示例：Spring Boot PATCH 接口

把前面策略组合成一个完整的用户资料修改接口（Map 方案，语义最精确）：

```java
@RestController
@RequestMapping("/api/users")
public class UserProfileController {

    @PatchMapping("/{id}")
    public Result<Void> updateProfile(@PathVariable Long id,
                                      @RequestBody Map<String, Object> updates) {
        if (updates == null || updates.isEmpty()) {
            throw new IllegalArgumentException("没有需要更新的字段");
        }

        ValidX validator = ValidX.init();

        // —— 账号标识：提交了就必须有效，不允许清空 ——
        if (updates.containsKey("email")) {
            validator.field("邮箱").notEmpty().isEmail(updates.get("email"));
        }
        if (updates.containsKey("phone")) {
            validator.field("手机号").notEmpty().isChinesePhone(updates.get("phone"));
        }

        // —— 普通资料：允许不更新，有值才校验格式 ——
        if (updates.containsKey("nickname")) {
            // 昵称等无专用验证器的字段，可在 Service 层做长度/敏感词规则；
            // 这里先做通用防注入字符拦截
            validator.field("昵称").isNotIn(updates.get("nickname"), FORBIDDEN_NICKNAMES);
        }
        if (updates.containsKey("birthday")) {
            Object birthday = updates.get("birthday");
            validator.field("生日").isDate(birthday);
            if (birthday != null && !birthday.toString().isEmpty()) {
                validator.field("生日").isPastDate(birthday);
            }
        }
        if (updates.containsKey("website")) {
            validator.field("个人主页").isUrl(updates.get("website"));
        }

        if (!validator.passed()) {
            throw new ValidationException(validator.getErrors());
        }

        userService.partialUpdate(id, updates);  // 按 Map 键动态拼 SQL，只更新提交字段
        return Result.ok();
    }
}
```

一条贯穿始终的原则：**能被 Map 的 `containsKey` 挡住的字段，连校验器都不进**——这是部分更新验证与全量验证最根本的差别。

## 总结

| 选择哪个方案 | 适用场景 | 核心语义 |
|------------|---------|---------|
| **方案一**：Map + `containsKey` 链式 | REST PATCH、要区分"缺失/null/清空" | 缺失字段不校验；`notEmpty()` 管"不允许清空" |
| **方案二**：UpdateDTO + null 即不更新 | 内部系统、字段不可置空 | 格式验证器对 null 放行 = 自动跳过未更新字段 |
| **方案三**：UpdateDTO + `@Valid` | Controller 声明式校验 | 只放格式注解；必填注解留给 CreateDTO |
| **进阶**：`""` 表达清空 | 需要"清空字段"能力 | 服务端把空串转 NULL，`null` 语义写进文档 |

三条心法收尾：

1. **判空与格式分离**是部分更新能成立的前提——必填规则（`@NotBlank`/`notEmpty()`）与格式规则（`@Email`/`isEmail`）各管一段，别混在一个注解里；
2. **校验范围由"提交了什么"决定**，不由 DTO 结构决定——Map 用 `containsKey`，DTO 用"null 即不更新"约定；
3. **更新接口永远单独建 DTO**，让 Create/Update 的规则差异显式化，比在同一个 DTO 上打补丁可靠得多。
