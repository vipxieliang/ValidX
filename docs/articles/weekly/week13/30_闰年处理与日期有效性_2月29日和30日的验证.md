## 引言

"2024-02-29 是生日，怎么存不了？""用户手动填了 2 月 30 日，居然通过校验了？""1900 年到底是不是闰年？"

日期有效性验证看似简单，实则暗藏三类边界：

1. **闰年规则**——`2024-02-29` 合法、`2023-02-29` 非法，且整百年份规则特殊（`2000` 是闰年、`1900` 不是）
2. **"日"的上限**——`2024-02-30` 永远非法（2 月最多 29 天），`2024-04-31` 同样非法
3. **解析模式的静默陷阱**——同一串 `2024-02-30`，在**严格模式（STRICT）**下被拒绝，在**智能模式（SMART）**下却会被悄悄"修正"成 `2024-02-29` 然后放行

ValidX 的日期验证家族里，不同注解用了**不同的解析策略**：`@Date`/`@DateTime` 显式使用 `ResolverStyle.STRICT`，严格拒绝无效日期；而 `@PastDate`/`@FutureDate` 系列未显式指定，实际走默认的 SMART 模式——这正是最容易踩坑的地方。

本文对照源码 + 单元测试，并附 Java 8 实测结果，把 2 月 29 日、2 月 30 日及各种边界日期的判定讲透。

> 文中所有 STRICT/SMART 行为均在本机 Java 8 实测验证，ValidX 版本 v1.2.0。

## 一、闰年规则：不只是"四年一闰"

闰年的完整定义（格里高利历）：

> 能被 4 整除的年份是闰年，但**能被 100 整除的年份除外**；不过**能被 400 整除的年份仍是闰年**。

用伪代码表达：

```
isLeap = (year % 4 == 0 && year % 100 != 0) || (year % 400 == 0)
```

| 年份 | 能被 4 整除 | 能被 100 整除 | 能被 400 整除 | 是否闰年 | 2月29日是否存在 |
|------|:---:|:---:|:---:|:---:|:---:|
| 2024 | ✅ | ❌ | ❌ | ✅ 闰年 | ✅ |
| 2023 | ❌ | ❌ | ❌ | ❌ | ❌ |
| 2000 | ✅ | ✅ | ✅ | ✅ 闰年 | ✅ |
| 1900 | ✅ | ✅ | ❌ | ❌ 平年 | ❌ |

**最容易错的是整百年份**：直觉上"能被 4 整除就是闰年"，但 1900 能被 4 和 100 整除、不能被 400 整除，**不是闰年**；而 2000 能被 400 整除，**是闰年**。

这也是为什么 ValidX 的单元测试专门覆盖了 `1900-02-29`（拒绝）与 `2000-02-29`（通过）——用世纪年用例防住"四年一闰"的简化直觉。

## 二、日期有效性：2月30日为什么永远不合法

各月天数固定：

| 月份 | 天数 | 备注 |
|------|------|------|
| 1、3、5、7、8、10、12 | 31 | 大月 |
| 4、6、9、11 | 30 | 小月 |
| 2（平年） | 28 | 只有平年 28 天 |
| 2（闰年） | 29 | 闰年多一天 |

因此：

- **`2024-02-30` 永不合法**——闰年 2 月最多也只有 29 天，不存在 30 日
- `2024-04-31` 不合法——4 月只有 30 天
- `2024-02-29` 仅在闰年合法；`2023-02-29` 因平年而非法

日期有效性验证 = **"格式对" + "日历真实存在"** 两个层次，格式正确（`2024-02-30` 符合 `yyyy-MM-dd`）不代表日历合法。ValidX 的 `@Date` 把这两层一起管住。

## 三、@Date：严格模式下的闰年判定

### 3.1 源码实现

`DateValidator` 创建格式化器时**显式指定了 `ResolverStyle.STRICT`**，并把 `yyyy` 替换为 `uuuu`（year-of-era → proleptic year，避免 STRICT 模式下需要 era 字段）：

```java
private static DateTimeFormatter createStrictFormatter(String pattern) {
    // 将 yyyy 替换为 uuuu 以支持 STRICT 模式
    String strictPattern = pattern.replace("yyyy", "uuuu")
                                 .replace("yy", "uu");
    return DateTimeFormatter.ofPattern(strictPattern, Locale.US)
            .withResolverStyle(ResolverStyle.STRICT);   // ← 严格模式
}
```

STRICT 模式下，`LocalDate.parse` 会**严格校验日历真实性**：不存在的一天直接抛 `DateTimeParseException`，验证器捕获后返回失败。

### 3.2 注解方式

```java
public class UserDTO {

    // 默认 yyyy-MM-dd，严格校验闰年与日历有效性
    @Date(message = "出生日期不合法")
    private String birthDate;

    // 自定义格式同样走严格模式
    @Date(pattern = "yyyy/MM/dd")
    private String anniversary;
}
```

官方单元测试（`DateFormatValidatorTest`）明确的判定矩阵：

| 输入 | 期望 | 说明 |
|------|:---:|------|
| `2024-02-29` | ✅ 通过 | 2024 是闰年 |
| `2023-02-29` | ❌ 拒绝 | 2023 是平年，2 月无 29 日 |
| `2024-02-30` | ❌ 拒绝 | 闰年 2 月也只有 29 天 |
| `2000-02-29` | ✅ 通过 | 整百年份中能被 400 整除 → 闰年 |
| `1900-02-29` | ❌ 拒绝 | 整百年份不能被 400 整除 → 平年 |

### 3.3 一个关键设计：空值放行

`@Date` 对 `null` 和 `""` 返回通过（与其他格式注解一致），"是否必填"交给判空注解：

```java
public class UserDTO {

    // 必填 + 严格日期：两注解组合，缺一不可
    @NotBlank(message = "出生日期不能为空")
    @Date(message = "出生日期不合法")
    private String birthDate;
}
```

## 四、@DateTime：带时间的闰年边界

`@DateTime`（如 `yyyy-MM-dd HH:mm:ss`）用于带时间部分的场景，日期部分**同样走 STRICT**，闰年判定与 `@Date` 完全一致：

```java
public class OrderDTO {

    @NotBlank
    @DateTime(pattern = "yyyy-MM-dd HH:mm:ss", message = "订单创建时间不合法")
    private String createdAt;
}
```

官方文档明确列出（README @DateTime 节）：

- ✅ `2024-02-29 23:59:59`（闰年）
- ❌ `2024-02-30 13:30:00`（无效日期）
- ❌ `2024-01-15 24:00:00`（小时 0-23）
- ❌ `2024-01-15 12:60:00`（分钟 0-59）
- ❌ `2024-01-15 12:30:60`（秒 0-59）

即：**日期有效性 + 时间范围**双层校验，不只是格式匹配。

## 五、链式 isDate / isDateTime

链式方式与注解共享同一套严格验证逻辑（`DateValidator.isValidDateFormat` / `DateTimeValidator.isValidDateTimeFormat`），行为完全一致：

```java
ValidX validator = ValidX.init();

// 严格模式判定闰年与日历有效性
validator.isDate("2024-02-29", "yyyy-MM-dd");  // 通过
validator.isDate("2023-02-29", "yyyy-MM-dd");  // 失败
validator.isDate("2024-02-30", "yyyy-MM-dd");  // 失败
validator.isDate("2000-02-29", "yyyy-MM-dd");  // 通过
validator.isDate("1900-02-29", "yyyy-MM-dd");  // 失败

// 默认格式（yyyy-MM-dd）
ValidX v2 = ValidX.init().isDate("2024-02-30");
// v2.passed() == false
```

链式测试（`DateFormatChainTest`）还覆盖了多值混验与 i18n 错误消息（如中文错误 "日期格式不正确"）。

业务里适合 Service 层动态校验：

```java
public void checkDateOfBirth(String birthDate) {
    ValidX validator = ValidX.init()
            .config(ValidXConfig.GLOBAL_NOT_EMPTY)      // 必填
            .field("出生日期").isDate(birthDate);        // 严格日期
    if (!validator.passed()) {
        throw new ValidationException(validator.getErrors());
    }
}
```

## 六、关键差异：PastDate/FutureDate 的 SMART 陷阱

### 6.1 源码实现差异

对照源码会发现**不一致**：

- `DateValidator` / `DateTimeValidator`：`withResolverStyle(ResolverStyle.STRICT)` **显式指定严格模式**
- `PastDateValidator` / `FutureDateValidator`：只做了 `yyyy→uuuu` 替换，**没有**调用 `.withResolverStyle(...)`，`DateTimeFormatter.ofPattern` 默认的 `ResolverStyle` 是 **SMART**

```java
// PastDateValidator.initialize —— 注意没有 .withResolverStyle(STRICT)！
String strictPattern = pattern.replace("yyyy", "uuuu")
                             .replace("yy", "uu");
this.formatter = DateTimeFormatter.ofPattern(strictPattern);  // 默认 SMART
```

### 6.2 SMART 的静默修正行为

`ResolverStyle.SMART` 会对明显不存在的日历日期做"聪明"的归一化，而不是拒绝：

| 输入 | STRICT | SMART |
|------|--------|-------|
| `2024-02-29` | 通过 | 通过 |
| `2023-02-29` | **拒绝** | **通过（修正为 2023-02-28）** |
| `2024-02-30` | **拒绝** | **通过（修正为 2024-02-29）** |
| `1900-02-29` | **拒绝** | **通过（修正为 1900-02-28）** |
| `2000-02-29` | 通过 | 通过 |
| `2024-04-31` | **拒绝** | **通过（修正为 2024-04-30）** |

**后果**：`@PastDate` / `@FutureDate`（以及对应的 `@PastDateTime`/`@FutureDateTime`）会把你以为"不存在"的 `2024-02-30` 悄悄当成 `2024-02-29` 参与过去/未来比较——**不会报格式错，而是静默放行（只要修正后的日期满足过去/未来条件）**。

### 6.3 为什么生日校验尤其危险

典型场景——用户注册填生日 `1990-02-30`：

```java
// ❌ 危险：SMART 把 1990-02-30 修正成 1990-02-28 直接通过
@PastDate
private String birthDate;   // "1990-02-30" 竟然校验通过

// ✅ 建议：先做严格日历校验，再做过去判断
@Date(message = "日期不合法")          // STRICT：1990-02-30 在此被拒
@PastDate(message = "生日必须早于今天")
private String birthDate;
```

> 同一字段**同时叠 `@Date`（严格格式/日历）与 `@PastDate`（过去语义）**，用前者补上后者的 SMART 漏洞，是这类场景的标准姿势。

## 七、实测对照：STRICT vs SMART

为保证结论不是纸上谈兵，用 Java 8 对本机行为做了实测（formatter 均为 `uuuu-MM-dd`）：

```
== 2024-02-29 ==
  STRICT => 通过 -> 2024-02-29
  SMART  => 通过 -> 2024-02-29
== 2023-02-29 ==
  STRICT => 拒绝 (DateTimeParseException)
  SMART  => 通过 -> 2023-02-28
== 2024-02-30 ==
  STRICT => 拒绝 (DateTimeParseException)
  SMART  => 通过 -> 2024-02-29
== 2024-04-31 ==
  STRICT => 拒绝 (DateTimeParseException)
  SMART  => 通过 -> 2024-04-30
== 1900-02-29 ==
  STRICT => 拒绝 (DateTimeParseException)
  SMART  => 通过 -> 1900-02-28
== 2000-02-29 ==
  STRICT => 通过 -> 2000-02-29
  SMART  => 通过 -> 2000-02-29
```

实测与 ValidX 测试/README 结论完全一致：

1. `@Date`/`@DateTime` 及链式 `isDate`/`isDateTime`（STRICT）：`2 月 29 日`仅在闰年通过，`2 月 30 日`永远拒绝，`1900/2000` 世纪年区分正确
2. `@PastDate`/`@FutureDate` 等（默认 SMART）：无效日期被**静默修正**而非拒绝

## 八、业务场景与最佳实践

| 场景 | 推荐注解 | 说明 |
|------|---------|------|
| 用户出生日期（需严格日历 + 过去） | `@Date` + `@PastDate`（或 `@PastDate` + `@Date`） | 双注解互补，杜绝 2 月 30 日 |
| 活动结束时间 | `@DateTime` + `@FutureDateTime`（如需严格） | 日期 + 时间双层严格 |
| 纯格式校验（不关心过去未来） | `@Date` / `@DateTime` | STRICT 已足够 |
| 运营录入的历史日期 | `@PastDate` | 若可接受 SMART 归一化再单独用 |
| Controller DTO 参数 | 注解 + `@Valid` | Spring 自动返回 400 |

**三条工程建议：**

1. **能用 `@Date`/`@DateTime` 就别依赖 `@PastDate`/`@FutureDate` 兜格式**——严格层与语义层分开声明，各管各的。
2. **涉及"必须真实存在"的业务字段（生日、合同签署日、证件日期）务必上严格校验**，否则 SMART 的归一化会悄悄改写用户数据。
3. **结合判空注解**：所有日期注解都放行 `null`/`""`，必填字段一定叠加 `@NotBlank`（链式则用 `config(GLOBAL_NOT_EMPTY)`/`notEmpty()`）。

> 延伸：ValidX 的 `@ChineseIdCard` 在身份证场景里会顺带校验出生日期段的合法性（同样需要正确处理闰年），身份证号中含 `19900229` 这类出生码时需注意。

## 总结

| 主题 | 结论 |
|------|------|
| 闰年规则 | `(y%4==0 && y%100!=0) || y%400==0`；1900 平年、2000 闰年 |
| 2月30日 | 永不合法，闰年 2 月最多 29 天 |
| `@Date`/`@DateTime` | STRICT 严格模式：`2024-02-29`✅、`2023-02-29`❌、`2024-02-30`❌、`1900`❌、`2000`✅ |
| 链式 `isDate`/`isDateTime` | 与注解同源，行为一致 |
| `@PastDate`/`@FutureDate` | 默认 SMART：`2024-02-30` 被静默修正为 `2024-02-29`，**不报错** |
| 最佳实践 | 严格日历（`@Date`）+ 语义（`@PastDate`）叠加使用；必填叠 `@NotBlank` |
| 空值 | 所有日期注解放行 `null`/`""`，判空单独负责 |

一句话记住本文核心：**判断"日期是否真实存在"用严格模式（`@Date`/`@DateTime`），判断"日期在过去还是未来"用语义注解，但别指望后者替你拒绝 2 月 30 日——它会悄悄帮你改成 2 月 29 日。**
