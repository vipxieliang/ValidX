# 时间戳验证：秒级与毫秒级的区分与应用

## 引言

三个真实事故：

1. **接口签名对不上**：服务端用 Java 生成签名，客户端用 PHP 验签。Java 的 `System.currentTimeMillis()` 返回 13 位毫秒，PHP 的 `time()` 返回 10 位秒，两边拿着不同长度的"时间戳"各自验签，永远对不上。
2. **订单时间倒退 52 年**：前端 JS `Date.now()` 返回 13 位毫秒，后端接口文档写的是"秒级时间戳"，数据入库时被当成秒直接存进 `BIGINT`，查询时转时间一看——1970 年。
3. **缓存刚设置就过期**：Redis `SETEX` 的过期时间被传成了毫秒，而 Redis 要的是秒，缓存有效期直接缩水 1000 倍。

这些事故的根源只有一个：**Unix 时间戳是数字，但"秒级"和"毫秒级"是两种不同的东西**。数字本身不会告诉你它的单位，混用了也不会报错——只是结果错得离谱。

本文先讲透秒级与毫秒级的本质区别，再对照 ValidX 的 `@Timestamp` 注解源码与测试用例，给出"如何在一进系统就把单位钉死"的完整方案。

> 说明：文中 ValidX 相关内容对照 v1.2.0 源码（`Timestamp` 注解、`TimestampValidator`）与测试用例（`TimestampValidatorTest`）核实，表格行为均可复现。

## 一、Unix 时间戳基础

### 1.1 定义

Unix 时间戳是**从 `1970-01-01 00:00:00 UTC` 起经过的时间计数**。它是个绝对数值，与任何时区无关——同一时刻，北京、纽约、伦敦拿到的都是同一个时间戳。

### 1.2 单位与位数

| 单位 | 当前时代位数 | 例子（2023-11-14 22:13:20 UTC） |
|------|:---:|------|
| 秒 | 10 位 | `1700000000` |
| 毫秒 | 13 位 | `1700000000000` |
| 微秒 | 16 位 | `1700000000000000` |
| 纳秒 | 19 位 | `1700000000000000000` |

> "位数判断法"只在当前时代成立：10 位 = 秒、13 位 = 毫秒。10 位秒级时间戳的上限是 `9999999999`，对应 **2286-11-20**——在那之前，位数判断法都有效。

### 1.3 各语言/平台的默认单位（混乱的源头）

| 语言 / 平台 | 常用取时间方式 | 单位 | 位数 |
|------------|--------------|------|:---:|
| Java | `System.currentTimeMillis()` | 毫秒 | 13 |
| Java | `Instant.now().getEpochSecond()` | 秒 | 10 |
| PHP | `time()` | 秒 | 10 |
| JavaScript | `Date.now()` | 毫秒 | 13 |
| Python | `time.time()` | 秒（浮点） | 10.xxx |
| Go | `time.Now().Unix()` / `.UnixMilli()` | 秒 / 毫秒 | 10 / 13 |
| MySQL | `UNIX_TIMESTAMP()` | 秒 | 10 |
| Redis | `TTL` / `SETEX` 过期时间 | 秒 | 10 |

**同一个"当前时间"，不同技术栈拿到的是不同单位的数字**——这就是跨端集成时时间戳必出问题的根本原因。

### 1.4 2038 问题

32 位有符号整数能表示的最大秒级时间戳是 `2147483647`，对应 **2038-01-19 03:14:07 UTC**。之后会溢出。虽然 Java 的 `long` 是 64 位没有此问题，但存量系统（C 程序、嵌入式、老数据库）若仍用 32 位 `int` 存秒，2038 年就是它们的"千年虫"。

## 二、秒与毫秒为什么会混：数量级灾难

### 2.1 混淆的两个方向

| 错误方向 | 结果 | 具体表现 |
|---------|------|---------|
| **毫秒当成秒** | 时间放大 1000 倍 | 当前时间戳 `1700000000000` 被当秒 → 公元 55879 年（远超范围） |
| **秒当成毫秒** | 时间缩小 1000 倍 | `1700000000` 被当毫秒 → `1970-01-20 17:33:20`，比真实时间晚了 52 年 |

第二种尤其隐蔽：**结果是"合法的时间"**（1970 年 1 月），不像第一种会明显爆掉。订单时间倒退回 1970 年、统计口径全乱、对账永远差 1000 倍，都是它。

### 2.2 典型事故场景

- **接口签名/防重放**：`timestamp` 字段单位不统一 → 签名永远验不过，或重放防护形同虚设；
- **支付回调**：回调里的 `time` 是秒，你按毫秒存 → 对账对不上；
- **缓存过期**：`SETEX key 300000` 传了毫秒 300000（5 分钟 × 60 × 1000 的数值却按秒解释）→ 缓存 3.5 天才过期；
- **数据库迁移**：`datetime` 转 `BIGINT` 时单位没统一 → 历史数据全部错位。

## 三、@Timestamp 注解深度解析

### 3.1 注解定义

```java
@Timestamp                   // 秒或毫秒均可
private String createTime;

@Timestamp(unit = TimestampUnit.SECONDS)       // 仅秒级（10 位）
private String createTimeSec;

@Timestamp(unit = TimestampUnit.MILLISECONDS)  // 仅毫秒级（13 位）
private String createTimeMs;
```

`unit` 有三种取值，默认 `ANY`：

| TimestampUnit | 接受范围 | 典型场景 |
|--------------|---------|---------|
| `SECONDS` | 10 位（秒） | 缓存过期、接口签名、Redis TTL |
| `MILLISECONDS` | 13 位（毫秒） | 业务时间、订单时间、日志时间 |
| `ANY` | 10 位或 13 位 | 第三方数据格式不确定时 |

### 3.2 双类型支持：String 与 Long

注解同时支持 `String` 和 `Long`（`Integer` 等其他 `Number` 也会转成 `Long` 处理）：

```java
@Timestamp
private String createTimeStr;   // "1700000000" / "1700000000000"

@Timestamp(unit = TimestampUnit.MILLISECONDS)
private Long createTimeLong;    // 1700000000000L
```

### 3.3 验证规则：两层把关

**String 类型**——正则 + 位数 + 范围三连：

1. 正则 `^\d+$` 要求纯数字（字母、空格、小数点、负数符号全部拒绝）；
2. 位数检查：`SECONDS` 必须 10 位、`MILLISECONDS` 必须 13 位、`ANY` 两者均可；
3. 位数对了再 `Long.parseLong` 验证数值范围（上限：秒 `9999999999`、毫秒 `9999999999999`）。

**Long 类型**——直接范围判断：

| unit | 通过条件 |
|------|---------|
| `SECONDS` | `0 ≤ value ≤ 9999999999` |
| `MILLISECONDS` | `9999999999 < value ≤ 9999999999999` |
| `ANY` | `0 ≤ value ≤ 9999999999999` |

注意 Long 的 `MILLISECONDS` 判定：**必须大于秒的上限**（`> 9999999999`），用数值范围区分单位，而不是位数。

### 3.4 实测行为表（来自项目测试用例）

| 输入 | ANY | SECONDS | MILLISECONDS |
|------|:---:|:---:|:---:|
| `"1700000000"`（10 位秒） | ✅ | ✅ | ❌ |
| `"1700000000000"`（13 位毫秒） | ✅ | ❌ | ✅ |
| `"0000000000"`（最小秒） | ✅ | ✅ | ❌ |
| `"9999999999"`（最大秒） | ✅ | ✅ | ❌ |
| `"17000000000"`（11 位） | ❌ | ❌ | ❌ |
| `"17000000000000"`（14 位） | ❌ | ❌ | ❌ |
| `"1700000abc"`（含字母） | ❌ | ❌ | ❌ |
| `" 1700000000 "`（含空格） | ❌ | ❌ | ❌ |
| `"1700000000.0"`（小数） | ❌ | ❌ | ❌ |
| `"-1700000000"`（负数） | ❌ | ❌ | ❌ |
| `1700000000L`（Long 秒） | ✅ | ✅ | ❌ |
| `1700000000000L`（Long 毫秒） | ✅ | ❌ | ✅ |
| `-1L`（Long 负数） | ❌ | ❌ | ❌ |
| `null` / `""` | ✅ 放行 | ✅ 放行 | ✅ 放行 |

> 与 ValidX 其他格式注解一致：**`null` 和空串放行**，"必填"请叠加 `@NotNull` / `@NotEmpty`。

## 四、链式 API 用法

动态数据（Map、JSON、单个参数）用链式方式就地校验：

```java
ValidX validator = ValidX.init()
        .field("时间戳").isTimestamp("1700000000");               // 默认 ANY

ValidX validator2 = ValidX.init()
        .field("创建时间").isTimestamp("1700000000000", Timestamp.TimestampUnit.MILLISECONDS);  // 指定毫秒

ValidX validator3 = ValidX.init()
        .field("过期时间").isTimestamp(1700000000L, Timestamp.TimestampUnit.SECONDS);           // 指定秒

if (!validator.isValid()) {
    throw new BusinessException(validator.getErrorMessage());
}
```

方法签名：

```java
public ValidX isTimestamp(Object value);                              // ANY
public ValidX isTimestamp(Object value, Timestamp.TimestampUnit unit); // 指定单位
```

## 五、秒级与毫秒级：如何选择与转换

### 5.1 选择标准：看精度需求

| 需求 | 推荐单位 | 理由 |
|------|---------|------|
| 接口签名、防重放 | 秒 | 精度到秒足够，且 10 位数更直观、跨端更不容易混 |
| 缓存过期、TTL | 秒 | Redis 等组件原生用秒 |
| 订单/业务时间 | 毫秒 | 同一秒内多笔操作需要区分先后 |
| 日志、埋点 | 毫秒（或微秒） | 定位问题需要高精度时序 |
| 跨系统传输 | **统一约定并校验** | 单位本身无优劣，混用才是灾难 |

### 5.2 转换公式与代码

```
秒 → 毫秒：× 1000
毫秒 → 秒：÷ 1000（整数除法）
```

```java
// 当前时间
long seconds = Instant.now().getEpochSecond();   // 10 位
long millis = System.currentTimeMillis();        // 13 位

// 互相转换
long millisFromSec = seconds * 1000;
long secFromMillis = millis / 1000;              // 毫秒部分被丢弃

// 时间戳 → 可读时间（注意指定时区）
LocalDateTime dt = LocalDateTime.ofInstant(
        Instant.ofEpochMilli(millis), ZoneId.systemDefault());
```

### 5.3 时区：时间戳的天然优势

时间戳是**绝对时刻**，本身不含时区。同一个 `1700000000` 在北京显示 `2023-11-15 06:13:20`，在纽约显示 `2023-11-14 17:13:20`——都是对的，因为它是同一时刻。**跨时区系统交换时间，用时间戳而不是 `yyyy-MM-dd HH:mm:ss` 字符串，可以从根上消灭时区 bug。**（字符串时间带时区规则，最容易出错。）

### 5.4 数据库存储

- 列类型用 `BIGINT`，禁止用 `INT`（32 位存秒有 2038 问题）；
- **全表统一单位**：要么全秒、要么全毫秒，用校验在入口钉死；
- 与 `datetime` 混用要小心：`datetime` 带时区语义（取决于数据库会话时区），时间戳不带，两者互转时先对齐时区。

## 六、电商场景落地

### 6.1 订单创建接口：钉死毫秒级

```java
public class OrderCreateDTO {
    @NotBlank
    private String orderNo;

    @NotNull
    @Timestamp(unit = Timestamp.TimestampUnit.MILLISECONDS,
            message = "下单时间必须是毫秒级时间戳")
    private Long createTime;
}
```

前端 `Date.now()` 传 13 位毫秒，后端严格校验——**前端传秒级或 11 位，直接 400**，单位问题在入口解决，而不是等数据进库后错乱。

### 6.2 支付回调验签 + 防重放

回调参数里的 `timestamp` 用于防重放，用秒级 + 时间窗口判断：

```java
public void handlePayCallback(PayNotifyDTO notify) {
    // 1. 校验时间戳格式（秒级）
    ValidX validator = ValidX.init()
            .field("回调时间戳").isTimestamp(notify.getTimestamp(), Timestamp.TimestampUnit.SECONDS);
    if (!validator.isValid()) {
        throw new BusinessException("回调时间戳格式错误");
    }

    // 2. 防重放：与服务器时间偏差超过 5 分钟，拒绝
    long now = Instant.now().getEpochSecond();
    if (Math.abs(now - notify.getTimestamp()) > 300) {
        throw new BusinessException("回调时间戳过期，可能存在重放攻击");
    }

    // 3. 验签（签名中通常也包含 timestamp）...
}
```

### 6.3 优惠券有效期：秒级 + 范围判断

```java
public class CouponDTO {
    @NotNull
    @Timestamp(unit = TimestampUnit.SECONDS, message = "生效时间必须是秒级时间戳")
    private Long startTime;

    @NotNull
    @Timestamp(unit = TimestampUnit.SECONDS, message = "失效时间必须是秒级时间戳")
    private Long endTime;
}
```

### 6.4 秒杀/限流时间窗口

```java
// 时间窗口按秒对齐，避免毫秒抖动导致窗口错位
long window = Instant.now().getEpochSecond() / 10;   // 每 10 秒一个窗口
redis.incr("seckill:window:" + window);
```

## 七、最佳实践清单

1. **入口钉死单位**：所有对外接口的 `timestamp` 字段一律用 `@Timestamp(unit = ...)` 校验，接收方定义清楚"只要秒"或"只要毫秒"；
2. **跨端文档写明单位**：接口文档里时间戳必须标注"秒级（10 位）还是毫秒级（13 位）"，这是大多数混用的根源；
3. **优先用秒级做跨系统传输**：位数少、直观、与 Redis/MySQL 等组件原生对齐；业务精度不足时再升级毫秒；
4. **数据库用 `BIGINT` 且全表统一**：禁止 `INT`（2038 问题），单位全表一致，混用时加迁移脚本一次性对齐；
5. **转换留痕**：秒↔毫秒转换只发生在明确定义的边界（如 Controller/Service 转换层），别散落在业务代码里；
6. **时间戳不带时区，传输首选**：跨时区系统交换时间用时间戳，别用 `yyyy-MM-dd HH:mm:ss` 字符串；
7. **必填显式声明**：`@Timestamp` 放行 `null`/空串，必填加 `@NotNull` / `@NotEmpty`；
8. **防重放配时间窗口**：签名校验时用 `|now - timestamp|` 限窗口，并拒绝未来时间戳。

## 总结

- Unix 时间戳是绝对时刻的数字，**秒（10 位）与毫秒（13 位）是两种不同单位**，混用不会报错但结果错得离谱（时间倒退 52 年 / 放大 1000 倍）；
- 不同技术栈默认单位不同（Java 毫秒、PHP 秒、JS 毫秒、MySQL 秒），跨端集成必须约定并校验单位；
- ValidX `@Timestamp` 支持 String/Long 双类型，`unit` 三种取值（`SECONDS` / `MILLISECONDS` / `ANY`），用**正则 + 位数 + 范围**三层把关，负数、非数字、位数不对一律拒绝；
- 单位本身无优劣，**统一 + 校验才是关键**：入口钉死单位，数据库 `BIGINT` 全表一致，跨端文档写明；
- 时间戳无时区，跨时区系统传输用时间戳，从根上消灭时区 bug。
