# 收货地址验证完整方案：省市区、邮编、详细地址

## 引言

一个地址引发的三场事故：

- **省市区乱填**：用户手动输入"北京市 海淀区 中关村大街"时把"北京"填进了省份字段、把"中关村大街"填进了市字段。订单生成后，配送系统按省市区路由快递网点，地址匹配失败，包裹在分拨中心多转了两天。
- **邮编与地址对不上**：用户在杭州，邮编随手填了 `100000`（北京市东城区的邮编）。商家发货时系统把邮编打印在面单上，分拣机按邮编投递，包裹发去了北京。
- **详细地址注入与超长**：详细地址字段没做长度和字符限制，用户提交了 500 字的地址外加一段 `<script>` 标签。订单系统把地址原样渲染到后台管理页，XSS 告警当天夜里响起。

这三个问题的共同点：**地址的"格式"和"合法性"是两回事，各字段需要不同的验证策略**。省市区没有正则可用，只能靠白名单；邮编有严格格式，必须 6 位数字；详细地址不该用正则，而要管长度、防注入。

本文用 ValidX 的能力逐层拆解：`@In` / `@Enum` 管省市区白名单、`@ChineseZipCode` 管邮编、`@Size` + `@NotContains` + 自定义注解管详细地址，最后给出可直接照抄的完整 `AddressDTO`。

> 说明：文中 ValidX 相关内容对照 v1.2.0 源码（`ChineseZipCode` 注解、`ChineseZipCodeValidator`、`In`/`Enum`/`NotContains` 注解）与测试用例（`ChineseZipCodeValidatorTest`、`ChineseZipCodeValidationChainTest`）核实，表格行为均可复现。项目基于 `javax.validation 2.0.1` + `Hibernate Validator 6.1.5`，标准注解 `@Size`/`@NotBlank` 开箱可用。

## 一、地址验证全景：四层模型

一份收货地址，从下单到配送，要守四个层面：

| 层级 | 验证对象 | 典型问题 | 谁来守 |
|------|---------|---------|--------|
| **区域层** | 省 / 市 / 区 | 乱填、别名、不一致 | 白名单（`@In` / `@Enum` / 自定义注解） |
| **邮编层** | 邮政编码 | 位数错、含字母、与区域不符 | `@ChineseZipCode` |
| **明细层** | 详细地址 | 超长、空串、注入字符 | `@Size` + `@NotContains` + 自定义 |
| **联系层** | 收件人姓名 / 电话 | 空、格式错 | `@ChineseName` / `@PhoneNumber` |

关键认知：**地址字段没有"万能正则"**。

- 省市区：34 个省级、300+ 地级、2800+ 县级行政区，**不存在能匹配"所有合法区划"的正则**，只能白名单；
- 邮编：有严格格式，`^\d{6}$` 就够了，ValidX 内置 `@ChineseZipCode`；
- 详细地址：允许中英文、数字、`-`、`#`、`栋`、`室` 等自由组合，**严格正则反而会误杀**，正确做法是管长度 + 管危险字符。

所以地址验证的正确姿势是**分层组合拳**：

```
省市区：白名单（@In / @Enum / 自定义 @Region）
邮编：  @ChineseZipCode
明细：  @NotBlank + @Size + @NotContains（+ 自定义）
联系：  @ChineseName / @PhoneNumber（见关联文章）
```

下面逐层展开。

## 二、省市区验证：白名单思想

### 2.1 为什么正则不管用

省市区字段最常见的错误是试图写"万能正则"（比如"只能中文和 ·"）。但这样的正则只能保证**长得像**，保证不了**是真的**：

- `北京市`、`北京省`、`北京是`——都能匹配"中文字符"正则，但只有第一个是合法区划；
- 区划还有直辖市特殊结构（北京市下辖 16 个区，没有"市"一级）、少数民族自治区的长名称（`新疆维吾尔自治区`）。

**结论：省市区只能做白名单校验**——判断"提交的值是否存在于合法区划集合中"。

### 2.2 小型白名单：直接用 @In

业务只覆盖少数地区时，`@In` 最直观。源码定义（`annotations/In.java`）：

```java
@Constraint(validatedBy = InValidator.class)
public @interface In {
    String[] value();                          // 白名单数组
    String message() default "{io.github.vipxieliang.validx.annotation.in}";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
```

用法：

```java
public class AddressDTO {

    /** 小范围白名单：只支持这几个城市 */
    @In(value = {"北京市", "上海市", "广州市", "深圳市", "杭州市"},
        message = "当前仅支持一二线城市配送")
    private String city;
}
```

`InValidator` 的行为（对照源码）：

| 输入 | 结果 | 说明 |
|------|:---:|------|
| 值在白名单中 | ✅ 通过 | 按 `String.valueOf(value)` 精确匹配 |
| 值不在白名单 | ❌ 拒绝 | 一个不匹配即失败 |
| `null` | ✅ 放行 | 必填请叠加 `@NotNull` |
| 集合 / 数组 | 逐个校验 | 每个元素都必须在白名单中 |

### 2.3 带编码的区划：用 @Enum

对接行政区划编码（如统计局 12 位区划代码）时，用 `@Enum` 管理更规范。源码定义（`annotations/Enum.java`）：

```java
@Constraint(validatedBy = EnumValidator.class)
public @interface Enum {
    Class<? extends java.lang.Enum<?>> target();   // 目标枚举
    String field() default "code";                 // 默认匹配枚举的 code 字段
    String message() default "{io.github.vipxieliang.validx.annotation.enum}";
    ...
}
```

用法：

```java
public enum Province {
    BEIJING("110000", "北京市"),
    SHANGHAI("310000", "上海市"),
    GUANGDONG("440000", "广东省"),
    ZHEJIANG("330000", "浙江省");

    private final String code;
    private final String name;

    Province(String code, String name) {
        this.code = code;
        this.name = name;
    }

    public String getCode() { return code; }
    public String getName() { return name; }
}

public class AddressDTO {

    /** 传省级编码，如 "110000" */
    @Enum(target = Province.class, field = "code", message = "省级区划编码不合法")
    private String provinceCode;
}
```

前端级联组件传编码、后端 `@Enum` 兜底，格式与合法性一次搞定。

### 2.4 生产方案：自定义 @Region 注解

全量 2800+ 区划写进注解不现实（类会爆炸、区划还经常调整）。生产环境更常见的做法是**行政区划数据（表/JSON/常量类）+ 自定义验证注解**。

ValidX 没有内置省市区注解——**这是刻意的边界**：行政区划是业务数据，且频繁变动（每年都有撤县设区），不该写死在验证库里。但它完全兼容标准 `@Constraint` 扩展，自定义一个也就 40 行：

```java
import javax.validation.Constraint;
import javax.validation.ConstraintValidator;
import javax.validation.ConstraintValidatorContext;
import javax.validation.Payload;
import java.lang.annotation.*;
import java.util.Set;

/** 区划类型 */
public enum RegionType { PROVINCE, CITY, DISTRICT }

/** 自定义：省市区白名单注解 */
@Target({ElementType.FIELD})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = RegionValidator.class)
public @interface Region {
    RegionType type();                            // 校验省级 / 市级 / 区级
    String message() default "区划名称不在合法范围内";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

/** 验证器：查静态区划集合（生产环境可换成查表/缓存） */
public class RegionValidator implements ConstraintValidator<Region, String> {

    private RegionType type;

    @Override
    public void initialize(Region constraintAnnotation) {
        this.type = constraintAnnotation.type();
    }

    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        if (value == null || value.isEmpty()) {
            return true;                          // 空值交给 @NotNull 处理
        }
        return RegionData.contains(type, value);
    }
}
```

配合行政区划数据源（示例结构）：

```java
/** 行政区划数据（生产环境建议用数据库表或启动时加载的 JSON） */
public final class RegionData {

    public static final Set<String> PROVINCES = Set.of(
            "北京市", "天津市", "上海市", "重庆市", "河北省", "山西省",
            "辽宁省", "吉林省", "黑龙江省", "江苏省", "浙江省", "安徽省",
            "福建省", "江西省", "山东省", "河南省", "湖北省", "湖南省",
            "广东省", "海南省", "四川省", "贵州省", "云南省", "陕西省",
            "甘肃省", "青海省", "台湾省", "内蒙古自治区", "广西壮族自治区",
            "西藏自治区", "宁夏回族自治区", "新疆维吾尔自治区",
            "香港特别行政区", "澳门特别行政区");

    public static final Set<String> CITIES = Set.of(/* ...300+ 地级市... */);

    public static final Set<String> DISTRICTS = Set.of(/* ...2800+ 县级区划... */);

    public static boolean contains(RegionType type, String name) {
        return switch (type) {
            case PROVINCE -> PROVINCES.contains(name);
            case CITY -> CITIES.contains(name);
            case DISTRICT -> DISTRICTS.contains(name);
        };
    }
}
```

> 注意：上例中的 `Set.of(/* ... */)` 只是示意，区划数据建议独立成表，行政区划调整时只需更新数据，不动代码。

用法（省、市、区三层各自白名单）：

```java
public class AddressDTO {

    @Region(type = RegionType.PROVINCE, message = "省份不合法")
    private String province;

    @Region(type = RegionType.CITY, message = "城市不合法")
    private String city;

    @Region(type = RegionType.DISTRICT, message = "区县不合法")
    private String district;
}
```

### 2.5 链式 API 场景

动态数据（前端直接传的省市区）用链式 API 就地校验：

```java
ValidX validator = ValidX.init()
        .field("省份").isIn(province, new String[]{"北京市", "上海市", "广东省", "浙江省"})
        .field("城市").isEnum(cityCode, Province.class, "code");

if (!validator.isValid()) {
    throw new BusinessException(validator.getErrorMessage());
}
```

链式方法的 `isIn`、`isEnum` 与注解 `@In`、`@Enum` 共用同一套验证器（`InValidator`、`EnumValidator`），行为完全一致。

## 三、邮编验证：@ChineseZipCode 深度解析

### 3.1 注解与规则

`@ChineseZipCode`（`annotations/ChineseZipCode.java`）是中国邮政编码专用注解：

```java
@Constraint(validatedBy = ChineseZipCodeValidator.class)
public @interface ChineseZipCode {
    String message() default "{io.github.vipxieliang.validx.annotation.chinese.zip.code}";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
```

验证规则只有一条（对照 `ChineseZipCodeValidator` 源码）：

```java
// 中国邮政编码正则：6 位数字
private static final String ZIP_CODE_PATTERN = "^\\d{6}$";
```

**6 位数字，不多不少**。

### 3.2 实测行为表（来自项目测试用例）

`ChineseZipCodeValidatorTest` 的断言结果：

| 输入 | 结果 | 说明 |
|------|:---:|------|
| `"100000"` | ✅ | 北京市东城区 |
| `"200000"` | ✅ | 上海市黄浦区 |
| `"518000"` | ✅ | 广东省深圳市 |
| `"610000"` | ✅ | 四川省成都市 |
| `"830000"` | ✅ | 新疆乌鲁木齐 |
| `"12345"` | ❌ | 位数不足（5 位） |
| `"1234567"` | ❌ | 位数过多（7 位） |
| `"12345a"` | ❌ | 含字母 |
| `"123 45"` | ❌ | 含空格 |
| `"123-456"` | ❌ | 含连字符 |
| `"12345@"` | ❌ | 含特殊字符 |
| `null` / `""` | ✅ 放行 | 必填请叠加 `@NotNull` |

> 与 ValidX 其他格式注解一致：**`null` 和空串放行**，"必填"请叠加 `@NotNull` / `@NotBlank`。

### 3.3 注解用法

```java
public class AddressDTO {

    @NotBlank(message = "邮编不能为空")
    @ChineseZipCode(message = "邮编必须是 6 位数字")
    private String zipCode;
}
```

### 3.4 链式 API

```java
ValidX validator = ValidX.init()
        .field("邮编").isChineseZipCode(zipCode);   // 对应 ValidX.isChineseZipCode(Object)

if (!validator.isValid()) {
    // 错误消息：邮政编码格式不正确
    throw new BusinessException(validator.getErrorMessage());
}
```

（链式调用失败时的错误消息"邮政编码格式不正确"可在 `ChineseZipCodeValidationChainTest` 中断言核实。）

### 3.5 进阶：邮编与省市区联动

`@ChineseZipCode` 只管"6 位数字"，不管"这个邮编属不属于这个省份"——那是**跨字段业务校验**。真实下单场景建议：

```java
public class AddressDTO {

    @NotNull
    @ChineseZipCode
    private String zipCode;

    @NotNull
    @Region(type = RegionType.PROVINCE)
    private String province;
}
```

邮编与省份的归属关系（比如 `100000` 对应北京）放**服务层**做跨字段校验，或者用自定义类级约束（Bean Validation 的 `@Constraint` 标注在类上、校验整个对象）。ValidX 定位是"格式校验库"，跨字段业务规则由业务层承担，职责更清晰。

## 四、详细地址验证：长度 + 黑名单 + 可扩展

### 4.1 为什么不用严格正则

详细地址的真实形态：

```
中关村大街 27 号院 2 号楼 3 单元 501 室
XX 大道 88 号 #1202
Building A, No. 66, Software Avenue
```

它天然混着中文、数字、字母、`-`、`#`、`·`、`栋/单元/室/号`。**写严格正则会误杀大量合法地址，不写正则又挡不住空串和注入**。所以正确策略是：**管长度 + 管危险字符 + 留扩展口**。

### 4.2 基础三件套

```java
public class AddressDTO {

    @NotBlank(message = "详细地址不能为空")
    @Size(min = 5, max = 120, message = "详细地址长度需在 5~120 字之间")
    @NotContains(value = {"<", ">", "\"", "'"}, message = "详细地址包含非法字符")
    private String detailAddress;
}
```

- `@NotBlank`：挡住空串和纯空格；
- `@Size`：挡住过短（`"1号"`）和过长（500 字）的输入；
- `@NotContains`（`annotations/NotContains.java`）：挡住 HTML 注入需要的 `< > " '`——XSS 攻击面直接砍掉。

`@NotContains` 参数说明（对照源码）：

| 参数 | 默认值 | 含义 |
|------|:---:|------|
| `value()` | 必填 | 禁止出现的子字符串数组 |
| `ignoreCase()` | `false` | 是否忽略大小写 |
| `matchAll()` | `true` | `true`=必须全都不包含（AND）；`false`=只要有一个不包含即通过（OR） |

### 4.3 更精细：自定义 @DetailAddress

如果规则要升级（比如强制不允许纯数字、不允许连续空白），用自定义注解扩展（ValidX 完全兼容标准 `@Constraint`）：

```java
@Constraint(validatedBy = DetailAddressValidator.class)
public @interface DetailAddress {
    int min() default 5;
    int max() default 120;
    String message() default "详细地址不合法";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class DetailAddressValidator
        implements ConstraintValidator<DetailAddress, String> {

    private int min;
    private int max;

    @Override
    public void initialize(DetailAddress constraintAnnotation) {
        this.min = constraintAnnotation.min();
        this.max = constraintAnnotation.max();
    }

    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        if (value == null || value.isEmpty()) {
            return true;
        }
        if (value.length() < min || value.length() > max) {
            return false;
        }
        // 规则扩展点：不允许全数字（缺少楼栋信息）、不允许连续多个空白等
        return !value.matches("^\\d+$") && !value.contains("  ");
    }
}
```

> 定位说明：ValidX 内置了 100+ 格式校验器，但不内置"详细地址"注解——因为地址规则因业务而异（跨境单要允许英文、同城单要限制特殊字符），留给你按业务自定义才是对的。

### 4.4 链式组合

```java
ValidX validator = ValidX.init()
        .field("详细地址").isNotContains(detail, new String[]{"<", ">"});
```

## 五、完整 AddressDTO 落地

把四层串起来，一个可直接使用的收货地址 DTO：

```java
public class AddressDTO {

    @NotBlank(message = "收件人姓名不能为空")
    @ChineseName(message = "收件人姓名格式不正确")
    private String receiverName;

    @NotBlank(message = "联系电话不能为空")
    @PhoneNumber(message = "联系电话格式不正确")
    private String phone;

    @NotNull(message = "省份不能为空")
    @Region(type = RegionType.PROVINCE, message = "省份不合法")
    private String province;

    @NotNull(message = "城市不能为空")
    @Region(type = RegionType.CITY, message = "城市不合法")
    private String city;

    @NotNull(message = "区县不能为空")
    @Region(type = RegionType.DISTRICT, message = "区县不合法")
    private String district;

    @NotBlank(message = "邮编不能为空")
    @ChineseZipCode(message = "邮编必须是 6 位数字")
    private String zipCode;

    @NotBlank(message = "详细地址不能为空")
    @Size(min = 5, max = 120, message = "详细地址长度需在 5~120 字之间")
    @NotContains(value = {"<", ">", "\"", "'"}, message = "详细地址包含非法字符")
    private String detailAddress;
}
```

订单 DTO 里嵌套引用，加 `@Valid` 触发递归校验：

```java
public class OrderCreateDTO {

    @NotBlank
    private String orderNo;

    @Valid                       // 关键：触发 AddressDTO 的校验
    private AddressDTO address;
}
```

### 5.1 与分组验证结合（创建必填 / 更新可空）

同一套地址在"下单"和"改收货人信息"里规则不同，用分组机制（详见同周文章《ValidX分组验证详解》）：

```java
public class AddressDTO {

    public interface SubmitGroup extends Default {}
    public interface EditGroup {}

    @NotNull(groups = SubmitGroup.class, message = "下单时省份必填")
    @Region(type = RegionType.PROVINCE, message = "省份不合法")
    private String province;

    @ChineseZipCode(message = "邮编必须是 6 位数字")   // 有值才校验格式
    private String zipCode;
}
```

```java
@PostMapping("/orders")
public Result createOrder(@Validated(AddressDTO.SubmitGroup.class) @RequestBody OrderCreateDTO dto) { ... }

@PutMapping("/address/{id}")
public Result editAddress(@Validated(AddressDTO.EditGroup.class) @RequestBody AddressDTO dto) { ... }
```

## 六、前端联动与后端校验的配合

### 6.1 职责分工

| 环节 | 做什么 | 用什么 |
|------|-------|--------|
| 前端 | 三级联动组件、格式提示 | 级联选择器 + 本地校验 |
| 后端 | **最终兜底**，防绕过前端 | ValidX 注解 + 白名单 |
| 服务层 | 跨字段规则（邮编归属、同城限制） | 业务校验 |

记住一条铁律：**前端校验是体验，后端校验是安全**。绕过前端直接 POST 的请求，只能靠后端兜住。

### 6.2 前端联动 + 后端白名单

前端级联组件保证"选出来的"都是合法区划；后端白名单保证"硬传的"也是合法区划。两边数据源用同一份区划表，避免"前端有、后端无"的错位。

---

## 七、最佳实践清单

1. **省市区永远用白名单，不写正则**：区划是枚举集合，正则只能验"长得像"；
2. **小范围用 `@In`，带编码用 `@Enum`，全量区划用自定义 `@Region`**：按业务范围选工具；
3. **邮编用 `@ChineseZipCode`**：`^\d{6}$`，格式的事交给它；邮编归属省份这种跨字段规则放服务层；
4. **详细地址管长度 + 黑名单，不写严格正则**：`@Size` + `@NotContains(< > " ')` 挡住超长与注入，规则要升级就自定义注解；
5. **`null`/空串放行、必填显式声明**：ValidX 格式注解一律放行空值，`@NotBlank`/`@NotNull` 补必填语义；
6. **嵌套对象加 `@Valid`**：`OrderCreateDTO` 里的 `AddressDTO` 不写 `@Valid` 不会递归校验；
7. **下单/编辑规则不同用分组**：`SubmitGroup extends Default` 与 `EditGroup` 分开，`@Validated(分组.class)` 触发；
8. **前端联动、后端兜底**：三级联动保证体验，白名单校验保证安全，数据源用同一份区划表；
9. **区划数据独立成表**：行政区划每年调整，数据与代码分离，改数据不发布代码。

---

## 总结

- 收货地址验证是**四层模型**：省市区（白名单）、邮编（格式）、详细地址（长度+黑名单）、联系人（姓名/电话）；
- ValidX 内置 `@ChineseZipCode`（邮编 6 位数字）、`@In`（白名单）、`@Enum`（枚举）、`@NotContains`（黑名单），覆盖地址验证 80% 的诉求；
- 省市区全量白名单和详细地址业务规则，用标准 `@Constraint` 自定义注解扩展——ValidX 完全兼容，这是它的设计边界：**格式校验内置，业务规则自定义**；
- 链式 API（`isChineseZipCode`、`isIn`、`isEnum`、`isNotContains`）与注解共用验证器，动态数据就地校验同样顺手；
- 下单/编辑规则不同用分组验证；嵌套对象记得 `@Valid`；前端联动、后端兜底，数据源同一份区划表。
